# 计数与点赞系统详解

> 笔记维度（点赞/收藏）与用户维度（关注/粉丝/发文/获赞/获收藏）的计数系统，以 Redis 为底层存储，采用**分片位图**实现幂等判重，**定制化 SDS 二进制紧凑计数**汇总计数，并通过 Kafka 写聚合和按需重建保证高并发下的数据可靠性。

## 二、核心数据结构

### 2.1 分片位图（Bitmap Shard）

**设计目标**：高效记录"哪些用户点赞了某内容"，实现幂等判重，并支持按位统计总数。

**为什么需要分片**：一个内容可能被数百万用户点赞，单键位图会膨胀到数 MB，成为 Redis 热点。分片后每片最多 `SHARD_SIZE`（如 65536）个 bit，多片分布存储。

```java
// BitmapShard.java
SHARD_SIZE = 65536 (2^16)

chunk = userId / SHARD_SIZE   // 定位第几个分片
bit   = userId % SHARD_SIZE   // 分片内的 bit 偏移
```

**Redis Key 格式**：
```
bm:{metric}:{entityType}:{entityId}:{chunk}
例：bm:like:knowpost:123456:0     (第 0 片，用户 0~65535)
    bm:like:knowpost:123456:1     (第 1 片，用户 65536~131071)
    bm:fav:knowpost:123456:0
```

### 2.2 SDS 汇总计数（Summary Data Structure）

**设计目标**：用极少的存储空间紧凑保存所有指标的计数快照，读取一次 GET 即可获得所有计数，无需额外计算。

**结构定义**（`CounterSchema`）：
```
固定长度：SCHEMA_LEN × FIELD_SIZE = 2 × 4 = 8 字节
字节布局：[like: 4字节 大端序 uint32] [fav: 4字节 大端序 uint32]
索引映射：like → idx=0 (offset=0), fav → idx=1 (offset=4)
```

**Redis Key 格式**：
```
cnt:{entityType}:{entityId}
例：cnt:knowpost:123456  → 8字节二进制值
```

**大端序（Big-Endian）读写示例**：
```
点赞数=1000，收藏数=500
字节序列：[0x00, 0x00, 0x03, 0xE8, 0x00, 0x00, 0x01, 0xF4]
           ←── like=1000 ───→ ←──── fav=500 ────→
```

### 2.3 用户维度 SDS（UserCounter）

```
固定长度：5 × 4 = 20 字节
字节布局：
  [0~3]  : followings（关注数）
  [4~7]  : followers（粉丝数）
  [8~11] : posts（发文数）
  [12~15]: likesReceived（获赞数）
  [16~19]: favsReceived（获收藏数）

Redis Key：ucnt:{userId}
```

## 三、点赞/收藏核心流程

### 3.1 点赞写流程（like）

```
用户请求 POST /api/v1/actions/like
{entityType, entityId}
  │
  ▼
CounterServiceImpl.like(entityType, entityId, userId)
  │
  ├─ 1. 计算分片定位
  │      chunk = userId / 65536
  │      bit   = userId % 65536
  │      bmKey = bm:like:{entityType}:{entityId}:{chunk}
  │
  ├─ 2. Lua 脚本原子切换（TOGGLE_LUA）
  │      GETBIT bmKey offset
  │      if prev == 1: return 0  (已点赞，幂等，不重复计数)
  │      SETBIT bmKey offset 1
  │      return 1                (状态从未点赞→已点赞，成功)
  │
  ├─ 3. 如果 Lua 返回 1（状态变化）
  │      ├─ 发布 Kafka 事件（异步聚合，delta=+1）
  │      │    CounterEvent{entityType, entityId, "like", idx=0, userId, delta=1}
  │      │    分区键 = entityId（保证同实体事件有序）
  │      └─ 发布本地 Spring 事件（触发缓存失效等快速路径）
  │
  └─ 4. 返回 true（成功）或 false（幂等跳过）
```

### 3.2 Lua 原子切换脚本

```lua
-- TOGGLE_LUA
local bmKey = KEYS[1]
local offset = tonumber(ARGV[1])
local op = ARGV[2]  -- 'add' or 'remove'
local prev = redis.call('GETBIT', bmKey, offset)
if op == 'add' then
    if prev == 1 then return 0 end  -- 已点赞，幂等
    redis.call('SETBIT', bmKey, offset, 1)
    return 1
elseif op == 'remove' then
    if prev == 0 then return 0 end  -- 已取消，幂等
    redis.call('SETBIT', bmKey, offset, 0)
    return 1
end
return -1
```

**Lua 脚本的必要性**：GETBIT + SETBIT 两步操作在非原子情况下可能产生竞态（两个用户同时点赞，都 GETBIT=0，都 SETBIT=1，但只应计数一次）。Lua 脚本在 Redis 中原子执行，彻底避免竞态。

### 3.3 Kafka 计数聚合（CounterAggregationConsumer）

```
Kafka Topic: counter-events（按 entityId 分区）
  │
  ▼
CounterAggregationConsumer（批量消费）
  │
  ├─ 将同一 entity 的多个增量先聚合到 Redis Hash（aggKey）
  │    aggKey = agg:{entityType}:{entityId}
  │    HINCRBY aggKey idx delta
  │
  └─ 定时（或批量触发）将 aggKey 中的增量合并到 SDS
       ├─ GETSET sdsKey 新值（原子更新）
       └─ HDEL aggKey idx（清理聚合桶）
```

**为什么用 Kafka 聚合写**：高并发场景下（如热门内容被同时点赞 1000 次），直接对 SDS 做 1000 次读改写会产生大量 RTT。通过 Kafka 将增量聚合，批量更新 SDS，大幅降低 Redis 写压力。

## 四、计数读取流程（getCounts）

```
CounterServiceImpl.getCounts(entityType, entityId, metrics)
  │
  ├─ 1. 读取 SDS：GET cnt:{entityType}:{entityId}
  │
  ├─ 2. 校验长度：raw.length == SCHEMA_LEN * FIELD_SIZE (8)
  │
  ├─ 如果 SDS 存在且长度正确（正常路径）
  │    └─ 大端序读取各字段值直接返回
  │
  └─ 如果 SDS 不存在或长度异常（需要重建）
       │
       ├─ 步骤 A：检查指数退避（inBackoff）
       │    如果在退避期内 → 返回全零（降级响应）
       │
       ├─ 步骤 B：限流检查（Redisson RateLimiter）
       │    每个实体 10 秒最多重建 3 次
       │    超限 → escalateBackoff（指数增加等待时间）→ 返回全零
       │
       ├─ 步骤 C：抢 Redisson 分布式锁（非阻塞 tryLock）
       │    lock.tryLock(0, MILLISECONDS)  # 0等待，立即返回
       │    抢不到 → escalateBackoff → 返回全零
       │
       └─ 步骤 D：持锁者执行重建
            ├─ 枚举位图分片：KEYS bm:{metric}:{entityType}:{entityId}:*
            ├─ 管道批量 BITCOUNT 求和：sum = Σ BITCOUNT(shard)
            ├─ 写入新 SDS：SET cnt:{entityType}:{entityId} <binary>
            ├─ 清理聚合桶：HDEL agg:{entityType}:{entityId} idx...
            └─ resetBackoff（重建成功，清除退避状态）
```

### 4.1 指数退避保护

**目的**：防止 SDS 频繁丢失时反复触发重建，保护 Redis。

```
backoff 键：
  backoff:sds-rebuild:until:{entityType}:{entityId}  → 下次允许尝试的时间戳
  backoff:sds-rebuild:exp:{entityType}:{entityId}    → 退避级别（指数）

退避时间：base_ms * 2^exp，最大 30 秒
  exp=0 → 500ms
  exp=1 → 1s
  exp=2 → 2s
  ...
  exp=6 → 32s → 截断为 30s
```

### 4.2 批量读取优化（getCountsBatch）

```java
// 管道批量 GET，减少多次 RTT
List<Object> raws = redis.executePipelined(connection -> {
    for (String k : sdsKeys) {
        connection.stringCommands().get(k.getBytes());
    }
    return null;
});
```

Feed 流场景下一页可能有 20 条内容，批量 GET 将 20 次 RTT 压缩为 1 次。

## 五、用户维度计数（UserCounterService）

### 5.1 增量更新（Lua 脚本）

```lua
-- INCR_FIELD_LUA：按索引原子更新 SDS 中某字段
local cntKey = KEYS[1]
local schemaLen = tonumber(ARGV[1])    -- 5（5个字段）
local fieldSize = tonumber(ARGV[2])    -- 4（每字段4字节）
local idx = tonumber(ARGV[3])          -- 字段索引（1-based）
local delta = tonumber(ARGV[4])        -- 增量

-- 读取当前值（不存在则用零填充）
local cnt = redis.call('GET', cntKey)
if not cnt then cnt = string.rep(string.char(0), schemaLen * fieldSize) end

-- 找到字段位置，读取当前值
local off = (idx - 1) * fieldSize
local v = read32be(cnt, off) + delta
if v < 0 then v = 0 end  -- 计数不能为负

-- 写回
local seg = write32be(v)
cnt = string.sub(cnt, 1, off) .. seg .. string.sub(cnt, off+fieldSize+1)
redis.call('SET', cntKey, cnt)
return 1
```

### 5.2 按需重建（rebuildAllCounters）

当用户维度 SDS 丢失时，从数据库重建：

```
1. 从 relation 表统计关注数/粉丝数（SQL COUNT）
2. 从 know_posts 表获取作者所有已发布知文 ID 列表
3. 批量查询各知文的 like/fav 计数（getCountsBatch）
4. 汇总得到 likesReceived / favsReceived
5. 写回 SDS
```

### 5.3 触发时机

| 事件 | 触发的计数更新 |
|------|--------------|
| 知文发布 | `incrementPosts(creatorId, +1)` |
| 有效点赞 | `incrementLikesReceived(authorId, +1)` |
| 取消点赞 | `incrementLikesReceived(authorId, -1)` |
| 有效收藏 | `incrementFavsReceived(authorId, +1)` |
| 关注成功 | `incrementFollowings(fromUserId, +1)`、`incrementFollowers(toUserId, +1)` |
| 取消关注 | `incrementFollowings(-1)`、`incrementFollowers(-1)` |

## 六、采样一致性校验

**问题**：SDS 中的计数是异步聚合的，可能与位图事实（BITCOUNT）存在短暂偏差。

**校验思路（可扩展）**：
1. 定时任务对部分实体采样，比较 SDS 值与 BITCOUNT 实际值
2. 偏差超出阈值则触发重建（`getCounts` 中的重建逻辑复用）
3. 重建完成后 SDS 与位图重新对齐

## 七、"灾难回放"机制

**CounterRebuildConsumer**（Kafka 消费者）：

当业务出现大规模 SDS 丢失（如 Redis 宕机重启）时，可以通过 Kafka 中历史事件重放来重建计数：

```
Kafka 存储历史消息（retention = 7天）
  │
  ▼
CounterRebuildConsumer
  │
  ├─ 消费所有 counter-events 历史消息
  ├─ 按 entityId 聚合所有 delta
  └─ 批量写入 SDS（从零开始重算）
```

## 八、是否点赞/收藏查询（isLiked / isFaved）

```
CounterServiceImpl.isLiked(entityType, entityId, userId)
  │
  ├─ chunk = userId / 65536
  ├─ bit   = userId % 65536
  ├─ key   = bm:like:{entityType}:{entityId}:{chunk}
  └─ GETBIT key bit → true/false
```

单次 GETBIT 操作，毫秒级响应，不依赖 SDS，不受重建影响。

## 九、Redis Key 汇总

| Key 格式 | 类型 | 说明 |
|----------|------|------|
| `bm:{metric}:{eType}:{eId}:{chunk}` | String（位图） | 点赞/收藏位图分片 |
| `cnt:{eType}:{eId}` | String（二进制） | 内容维度 SDS（8字节） |
| `agg:{eType}:{eId}` | Hash | 增量聚合桶 |
| `ucnt:{userId}` | String（二进制） | 用户维度 SDS（20字节） |
| `lock:sds-rebuild:{eType}:{eId}` | Redisson Lock | 重建分布式锁 |
| `rl:sds-rebuild:{eType}:{eId}` | Redisson RateLimiter | 重建限流 |
| `backoff:sds-rebuild:until:{eType}:{eId}` | String | 退避截止时间戳 |
| `backoff:sds-rebuild:exp:{eType}:{eId}` | String | 退避指数级别 |
| `rl:follow:{userId}` | Hash | 关注操作令牌桶 |

## 十、设计亮点与学习要点

1. **位图分片（Bitmap Sharding）**：解决单键热点和内存膨胀问题，将大量用户 ID 分散到多个 key
2. **Lua 脚本原子性**：GETBIT + SETBIT 两步操作必须原子，防止并发竞态导致计数偏差
3. **SDS 二进制紧凑编码**：相比 Hash 结构（每字段独立存储），SDS 一次 GET 获取所有计数，内存更小、读取更快
4. **大端序（Big-Endian）**：网络标准字节序，Java 侧手动编解码（不依赖框架序列化）
5. **三重保护（限流+退避+分布式锁）**：防止 SDS 丢失时引发重建风暴
   - Redisson RateLimiter：每 10 秒最多重建 3 次
   - 指数退避：失败后等待时间倍增，最大 30 秒
   - 分布式锁：确保同一时刻只有一个节点执行重建
6. **管道批量读取（Pipeline）**：Feed 流场景批量读 SDS，将 N 次 RTT 优化为 1 次
7. **Kafka 写聚合**：高并发写场景下先聚合增量，再批量更新 SDS，避免频繁读改写
8. **灾难回放**：Kafka 7 天消息保留期作为"事件日志"，极端故障后可完整重建计数
