# 登录流程详解

> 登录支持两种凭证通道：**密码登录**和**验证码登录**。两种通道共享同一个接口和大部分校验逻辑，只在凭证验证那一步分叉。

---

## 一、整体流程概览

### 通道一：密码登录（直接一步）

```
前端
 │  POST /api/v1/auth/login
 │  { identifierType:"PHONE", identifier:"138xxxx", password:"Abc12345" }
 │ ───────────────────────────────────────────────────────────────────►│
 │                                                                      │
 │                              格式校验 → 查用户 → BCrypt 密码比对    │
 │                              → 签发令牌对 → 存白名单 → 记审计日志   │
 │ ◄───────────────────────────────────────────────────────────────────│
 │  { user:{...}, token:{ accessToken, refreshToken, ... } }
```

### 通道二：验证码登录（需要先发验证码）

```
前端
 │  第一步：POST /api/v1/auth/send-code
 │  { scene:"LOGIN", identifierType:"PHONE", identifier:"138xxxx" }
 │ ───────────────────────────────────────────────────────────────────►│
 │                              格式校验 → 账号必须存在 → 速率限制     │
 │                              → 生成验证码 → 存 Redis → 发送        │
 │ ◄───────────────────────────────────────────────────────────────────│
 │  { identifier, scene, expireSeconds:300 }
 │
 │  第二步：POST /api/v1/auth/login
 │  { identifierType:"PHONE", identifier:"138xxxx", code:"483920" }
 │ ───────────────────────────────────────────────────────────────────►│
 │                              格式校验 → 查用户 → 验证码校验        │
 │                              → 签发令牌对 → 存白名单 → 记审计日志   │
 │ ◄───────────────────────────────────────────────────────────────────│
 │  { user:{...}, token:{ accessToken, refreshToken, ... } }
```

## 二、发送验证码（验证码登录的前置步骤）

`scene = LOGIN` 时调用 `POST /api/v1/auth/send-code`，与注册发码流程基本相同，区别只有一处：

**注册场景**：要求账号**不存在**（防止已注册账号重复注册）
**登录场景**：要求账号**必须存在**（不存在说明还没注册，无法登录）

```java
// AuthService.sendCode()
boolean exists = identifierExists(request.identifierType(), normalized);
if (request.scene() == VerificationScene.LOGIN && !exists) {
    throw new BusinessException(ErrorCode.IDENTIFIER_NOT_FOUND);  // 账号不存在
}
```

其余速率限制、Redis 存储、发送逻辑与注册完全一致，详见《注册流程详解》第二节。

## 三、登录接口详解：AuthService.login()

### 接口信息

```
POST /api/v1/auth/login
（SecurityConfig 中配置为 permitAll，无需登录）
```

### 请求体

```java
// LoginRequest.java
public record LoginRequest(
    @NotNull  IdentifierType identifierType,  // PHONE / EMAIL
    @NotBlank String identifier,              // 手机号或邮箱
    String code,       // 验证码（验证码通道填写，与 password 二选一）
    String password    // 密码（密码通道填写，与 code 二选一）
) {}
```

`code` 和 `password` 都是可选字段（没有 `@NotBlank`），但至少要传一个，否则 Service 层会抛错。

### 完整代码

```java
// AuthService.java
public AuthResponse login(LoginRequest request, ClientInfo clientInfo) {

    // ① 格式校验 + 标准化
    validateIdentifier(request.identifierType(), request.identifier());
    String identifier = normalizeIdentifier(request.identifierType(), request.identifier());

    // ② 查用户（账号不存在直接返回错误）
    Optional<User> userOptional = findUserByIdentifier(request.identifierType(), identifier);
    if (userOptional.isEmpty()) {
        throw new BusinessException(ErrorCode.IDENTIFIER_NOT_FOUND);
    }
    User user = userOptional.get();

    // ③ 凭证验证（两个通道分叉）
    String channel;
    if (StringUtils.hasText(request.password())) {
        // ── 通道一：密码登录 ────────────────────────
        channel = "PASSWORD";
        if (!StringUtils.hasText(user.getPasswordHash()) ||
            !passwordEncoder.matches(request.password(), user.getPasswordHash())) {
            // 密码错误：记录 FAILED 审计日志
            loginLogService.record(user.getId(), identifier, channel,
                                   clientInfo.ip(), clientInfo.userAgent(), "FAILED");
            throw new BusinessException(ErrorCode.INVALID_CREDENTIALS);
        }
    } else if (StringUtils.hasText(request.code())) {
        // ── 通道二：验证码登录 ──────────────────────
        channel = "CODE";
        ensureVerificationSuccess(
            verificationService.verify(VerificationScene.LOGIN, identifier, request.code())
        );
    } else {
        // ── 两者都没传 ───────────────────────────────
        throw new BusinessException(ErrorCode.BAD_REQUEST, "请提供验证码或密码");
    }

    // ④ 签发 JWT 令牌对
    TokenPair tokenPair = jwtService.issueTokenPair(user);

    // ⑤ Refresh Token 存入 Redis 白名单
    storeRefreshToken(user.getId(), tokenPair);

    // ⑥ 记录成功审计日志
    loginLogService.record(user.getId(), identifier, channel,
                           clientInfo.ip(), clientInfo.userAgent(), "SUCCESS");

    // ⑦ 组装响应
    return new AuthResponse(mapUser(user), mapToken(tokenPair));
}
```

## 四、两种通道的凭证验证细节

### 通道一：密码登录（BCrypt 比对）

```java
// 条件：request.password() 非空
channel = "PASSWORD";

boolean valid =
    StringUtils.hasText(user.getPasswordHash())         // 用户是否设置了密码
    && passwordEncoder.matches(                          // BCrypt 比对
           request.password(),       // 用户输入的明文密码
           user.getPasswordHash()    // 数据库中的 BCrypt 哈希
       );

if (!valid) {
    // ★ 密码通道特有：失败时先记录 FAILED 审计日志，再抛异常
    loginLogService.record(..., "FAILED");
    throw new BusinessException(ErrorCode.INVALID_CREDENTIALS);
}
```

**BCrypt 比对的原理**：BCrypt 哈希格式为 `$2a$12$<22位盐><31位哈希>`，`passwordEncoder.matches()` 从哈希值中取出盐，对输入的明文重新哈希，然后比较结果——因此即使数据库哈希泄露，也无法反推出原始密码。

**两种失败场景**：
- `user.getPasswordHash()` 为 null 或空：该用户注册时没有设置密码（仅验证码注册），无法用密码登录 → `INVALID_CREDENTIALS`
- 密码输入错误：BCrypt 比对不通过 → `INVALID_CREDENTIALS`

注意：两种场景返回同一个错误码，**不区分"未设置密码"和"密码错误"**，防止信息泄露（攻击者无法探测账号是否设置了密码）。

### 通道二：验证码登录（Redis Hash 校验）

```java
// 条件：request.code() 非空（且 password 为空）
channel = "CODE";

ensureVerificationSuccess(
    verificationService.verify(VerificationScene.LOGIN, identifier, request.code())
);
```

`verify()` 内部的完整逻辑（从 `RedisVerificationCodeStore`）：

```
键名：auth:code:LOGIN:138xxxx

① 读取 Redis Hash 的全部字段
   → 键不存在（从未发码 / 已过期 / 已用过）→ NOT_FOUND → 抛 VERIFICATION_NOT_FOUND

② 检查尝试次数
   → attempts >= maxAttempts（5次）→ TOO_MANY_ATTEMPTS → 抛 VERIFICATION_TOO_MANY_ATTEMPTS

③ 比对验证码
   → 匹配：删除 Redis 键（一次性），返回 SUCCESS → 继续登录流程
   → 不匹配：attempts + 1，写回 Redis
     → 若刚好达到上限：延长 TTL 至 30 分钟（防止通过等待过期来重置次数）
     → 返回 MISMATCH → 抛 VERIFICATION_MISMATCH
```

**验证码通道与密码通道的一个区别**：验证码登录失败时**不记录 FAILED 审计日志**，密码登录失败时会记录。这是设计上的取舍——密码错误更值得追踪（可能是暴力破解），验证码错误更可能是用户手误。

## 五、步骤对比：注册 vs 登录

| 步骤 | 注册 | 密码登录 | 验证码登录 |
|---|---|---|---|
| 格式校验 | ✅ | ✅ | ✅ |
| 协议同意检查 | ✅ | ❌ | ❌ |
| 账号唯一性校验 | ✅（必须不存在） | ❌ | ❌ |
| 查用户 | ❌（创建） | ✅（必须存在） | ✅（必须存在） |
| 密码校验 | ❌ | ✅（BCrypt 比对） | ❌ |
| 验证码校验 | ✅（必填） | ❌ | ✅（必填） |
| 密码哈希存储 | 可选 | ❌ | ❌ |
| 创建用户 | ✅ | ❌ | ❌ |
| 签发令牌对 | ✅ | ✅ | ✅ |
| 白名单存储 | ✅ | ✅ | ✅ |
| 记录审计日志 | ✅（成功） | ✅（成功+失败） | ✅（成功） |

## 六、审计日志（LoginLog）

登录成功/失败都会写入 `login_log` 表：

```java
// LoginLog.java 的字段
Long    id          // 自增主键
Long    userId      // 用户 ID
String  identifier  // 登录使用的账号（手机号/邮箱）
String  channel     // 渠道：PASSWORD / CODE
String  ip          // 客户端 IP
String  userAgent   // 浏览器 UA
String  status      // SUCCESS / FAILED
Instant createdAt   // 时间戳
```

`channel` 字段的设计让管理员可以统计哪种登录方式更常用，以及追踪特定账号的密码失败记录（判断是否遭受暴力破解攻击）。

## 七、客户端 IP 的提取

Controller 层在转发请求前，先从 HTTP Header 中提取客户端真实 IP：

```java
// AuthController.java
private String extractClientIp(HttpServletRequest request) {
    // 优先级1：X-Forwarded-For 的第一个地址（经过反向代理时的真实 IP）
    String forwarded = request.getHeader("X-Forwarded-For");
    if (forwarded != null && !forwarded.isBlank()) {
        return forwarded.split(",")[0].trim();
    }
    // 优先级2：X-Real-IP（Nginx 常用）
    String realIp = request.getHeader("X-Real-IP");
    if (realIp != null && !realIp.isBlank()) {
        return realIp.trim();
    }
    // 兜底：直连 IP（本地开发时通常是 127.0.0.1）
    return request.getRemoteAddr();
}
```

`X-Forwarded-For` 可能包含多个 IP（如 `客户端IP, 代理1IP, 代理2IP`），取第一个才是真实客户端 IP。

## 九、登录失败的各种场景

| 场景 | 错误码 | 备注 |
|---|---|---|
| 账号格式不合法（手机/邮箱正则不匹配） | `BAD_REQUEST` | 格式校验阶段 |
| 账号不存在 | `IDENTIFIER_NOT_FOUND` | 查用户阶段 |
| 密码和验证码都没传 | `BAD_REQUEST` | 凭证通道判断阶段 |
| 密码错误 / 未设置密码 | `INVALID_CREDENTIALS` | 统一错误码，不区分两种情况 |
| 验证码不存在/已过期 | `VERIFICATION_NOT_FOUND` | 未发码或 5 分钟内已用完 |
| 验证码填写错误 | `VERIFICATION_MISMATCH` | 剩余尝试次数 N-1 次 |
| 验证码错误次数超上限 | `VERIFICATION_TOO_MANY_ATTEMPTS` | 触发 30 分钟锁定 |

---

## 十、一句话总结

> 登录 = 格式校验 → 查用户 → **分叉**（密码通道：BCrypt 比对；验证码通道：Redis Hash 校验）→ 两通道合并 → 签发令牌对 → 白名单存储 → 审计日志 → 返回 `{ user, token }`。
