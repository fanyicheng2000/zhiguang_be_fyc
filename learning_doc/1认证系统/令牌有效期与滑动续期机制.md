# 令牌有效期与滑动续期机制

> **你的问题**：每次刷新都生成全新的 Refresh Token（有效期重置为 7 天），那只要用户每 7 天内访问一次，岂不是永远不用重新登录？这是主流设计吗？
>
> **结论**：你的理解完全正确。这种机制叫**滑动窗口续期（Sliding Window Renewal）**，确实是目前大多数主流互联网平台的标准设计。

---

## 一、用代码验证你的理解

每次调用刷新接口，最终都会执行 `JwtService.issueTokenPair()`：

```java
// JwtService.java
public TokenPair issueTokenPair(User user) {
    Instant issuedAt = Instant.now(clock);   // ← 永远是"当前时刻"

    // Access Token 过期时间 = 当前时刻 + 15 分钟
    Instant accessExpiresAt  = issuedAt.plus(properties.getJwt().getAccessTokenTtl());

    // Refresh Token 过期时间 = 当前时刻 + 7 天  ← 每次都重新计算！
    Instant refreshExpiresAt = issuedAt.plus(properties.getJwt().getRefreshTokenTtl());

    // ...
}
```

结论：**每次刷新，新 Refresh Token 的有效期都从当前时刻起重新算 7 天**，而不是从最初登录时起算固定 7 天。

Redis 白名单的 TTL 也同步更新（`storeRefreshToken` 里用的是令牌的绝对过期时间减去当前时间）：

```java
// AuthService.storeRefreshToken()
Duration ttl = Duration.between(Instant.now(), tokenPair.refreshTokenExpiresAt());
// 每次都是新令牌的 7 天 TTL，旧键被删除，新键被写入
refreshTokenStore.storeToken(userId, tokenPair.refreshTokenId(), ttl);
```

## 二、滑动窗口续期的完整时间线

假设用户周期性地每 3 天访问一次：

```
Day 0   用户登录
        → Access Token 有效至 Day 0 + 15min
        → Refresh Token 有效至 Day 7

        ↓（15 分钟后 Access Token 过期）

Day 0   前端触发静默刷新
        → 新 Access Token 有效至 Day 0 + 15min（新的）
        → 新 Refresh Token 有效至 Day 7（从现在起重新算）

        ↓（用户继续使用，每 15 分钟刷新一次令牌）

Day 3   用户再次活跃，触发刷新
        → 新 Refresh Token 有效至 Day 3 + 7 = Day 10  ← 窗口向右滑动了！

Day 6   用户再次活跃
        → 新 Refresh Token 有效至 Day 6 + 7 = Day 13  ← 再次滑动

Day 13  用户再次活跃（距上次 7 天内）
        → 新 Refresh Token 有效至 Day 20              ← 继续滑动

        ↓（只要访问间隔不超过 7 天）

Day N   用户永远不需要重新登录   ← 你的理解完全正确
```

只要用户在旧 Refresh Token 过期之前触发过一次刷新，有效期就重置为 7 天，如此循环。

## 三、什么时候用户会被强制重新登录？

有且只有以下几种情况：

| 场景 | 原因 |
|---|---|
| **用户连续 7 天未打开 App/网页** | Refresh Token 自然过期，Redis 键 TTL 到零自动消失 |
| **用户主动点击"退出登录"** | `logout` 接口撤销当前 Refresh Token（从 Redis 删除） |
| **用户修改了密码** | `resetPassword` 调用 `revokeAll(userId)`，删除该用户所有 Refresh Token |
| **管理员强制下线** | 若实现了后台管理，同样可调用 `revokeAll(userId)` |

## 四、这是主流设计吗？

是的，这是目前绝大多数互联网产品的标准做法，叫做**滑动窗口（Sliding Window）**策略，与之对应的还有**固定过期（Absolute Expiry）**策略：

### 对比：两种策略

| | 固定过期 | 滑动窗口（本项目） |
|---|---|---|
| **有效期计算基准** | 从首次登录起算，固定到期 | 每次刷新时重置，从当前时刻起算 |
| **行为活跃用户** | 到期必须重新登录 | 只要持续活跃，永不过期 |
| **行为不活跃用户** | 到期后过期 | 超过 7 天不访问，过期 |
| **安全性** | 较高（令牌有绝对寿命上限） | 稍低（活跃用户令牌可无限续期） |
| **用户体验** | 较差（活跃用户也会被踢） | 较好（用户无感知） |

### 主流平台的实践

- **微信**：登录后长期有效，很少要求重新登录（典型滑动窗口）
- **支付宝**：日常操作无感知续期，但敏感操作（转账等）额外要求指纹/密码二次验证
- **Google / Gmail**：基本不会主动退出，除非长时间不用或安全事件
- **GitHub**：Personal Access Token 可设置为永不过期或固定日期到期（提供两种选择）
- **微博、抖音、知乎**：活跃用户基本无感知，长期不用才会被踢

**结论**：对于 C 端产品（面向普通用户的 App / 网页），滑动窗口是行业默认选择，因为用户体验优先——没人希望每隔几天就被强制重新登录。

## 五、本项目设计的安全权衡

采用滑动窗口的代价是：**如果 Refresh Token 被盗，只要攻击者持续活跃，理论上可以永久持有会话**。

本项目用**令牌轮换（Token Rotation）**来缓解这个风险：
- 每次刷新，旧 Refresh Token 立即作废
- 同一个 Refresh Token 只能用一次
- 旧 RT 被使用后，受害者使用同一个旧 RT 会得到 401，能够感知到异常

但如果攻击者比受害者先刷新，他就得到了新 RT，受害者反而被踢出。这个情况下只有**主动改密码**才能彻底清除攻击者（`resetPassword` 调用 `revokeAll`，删除所有 RT）。

## 六、如果要实现"固定过期"该怎么改？

当前代码每次都从 `Instant.now()` 起算 7 天：

```java
// 现在的实现（滑动窗口）
Instant refreshExpiresAt = issuedAt.plus(properties.getJwt().getRefreshTokenTtl());
```

如果想改成固定过期，需要在登录时把**首次登录时间**记录下来，刷新时用固定时间点计算剩余 TTL：

```java
// 固定过期的实现思路（本项目未采用）
Instant loginTime = ...;  // 首次登录时间（需额外存储）
Instant absoluteExpiry = loginTime.plus(Duration.ofDays(7));
// 刷新时新 RT 的 exp = absoluteExpiry（固定不变）
// 当 absoluteExpiry < now 时，刷新失败，强制重新登录
```

本项目没有实现这个，因为对 C 端产品来说没有必要——强制 7 天后重登只会降低用户体验，并不显著提升安全性。

---

## 七、总结

> - **你理解完全正确**：只要用户每 7 天内活跃一次，Refresh Token 就会持续滑动续期，永远不会过期，用户永远不需要重新登录。
> - **这是主流设计**：微信、支付宝、Google 等几乎所有 C 端产品都采用这种策略，用户体验优先。
> - **安全兜底**：令牌轮换 + 改密码强制下线，是面对 RT 泄露时的应对手段。
> - **本项目的选择**是合理的：对于一个知识内容平台，用户体验比严格的会话生命周期管理更重要。
