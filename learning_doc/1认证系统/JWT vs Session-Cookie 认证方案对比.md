# JWT vs Session/Cookie 认证方案对比

> **你的问题**：JWT 相比 Session/Cookie 有哪些优势？Session 和 Cookie 是怎么用的？

---

## 一、从零开始：HTTP 是无状态的

理解这个问题，先要理解一个基本事实：**HTTP 协议本身是无状态的**。

什么叫无状态？每个 HTTP 请求对服务器来说都是陌生人：

```
第一次请求：你好，我是用户张三，我的密码是 123456
服务器：验证通过，你好张三！

第二次请求：帮我查一下我的订单
服务器：你是谁？我不认识你。
```

每次请求结束，服务器就"忘"了你是谁。但网站显然需要记住登录状态，于是出现了两种解决思路：**把状态存在服务端（Session 方案）** 和 **把状态存在客户端令牌里（JWT 方案）**。

---

## 二、Session/Cookie 方案：状态存服务端

### 完整工作流程

```
第一步：用户登录
┌──────────────────────────────────────────────────────────────┐
│  浏览器                          服务器                        │
│                                                               │
│  POST /login                                                  │
│  { username, password } ────────►  验证密码成功              │
│                                                               │
│                                    在内存（或 Redis）里创建：  │
│                                    Session {                  │
│                                      sessionId: "abc123xyz",  │
│                                      userId: 10001,           │
│                                      username: "张三",         │
│                                      loginTime: ...,          │
│                                      expiresAt: ...           │
│                                    }                          │
│                                                               │
│  ◄────────────────────────────── HTTP 响应                    │
│  Set-Cookie: JSESSIONID=abc123xyz; HttpOnly; Secure; Path=/   │
│  （浏览器自动把这个 Cookie 存下来）                           │
└──────────────────────────────────────────────────────────────┘

第二步：后续每个请求
┌──────────────────────────────────────────────────────────────┐
│  浏览器                          服务器                        │
│                                                               │
│  GET /api/orders                                              │
│  Cookie: JSESSIONID=abc123xyz   ────►                        │
│  （浏览器自动携带，不需要前端任何代码）                       │
│                                                               │
│                                    用 abc123xyz 查 Session 表  │
│                                    → 找到：userId = 10001     │
│                                    → 以张三的身份处理请求      │
│                                                               │
│  ◄────────────────────────────── 返回张三的订单数据           │
└──────────────────────────────────────────────────────────────┘
```

**关键特征**：
- 服务端存储用户状态（Session 数据）
- 客户端只存一个 `sessionId`（一串随机字符，本身不含任何信息）
- Cookie 由浏览器自动携带，前端代码无需干预

### Session 存在哪里

最简单的情况：存在服务器进程内存里。

```
服务器内存：
HashMap<sessionId, Session> sessions = {
    "abc123xyz" → { userId:10001, name:"张三", ... },
    "def456uvw" → { userId:10002, name:"李四", ... },
    "ghi789rst" → { userId:10003, name:"王五", ... },
    ...
}
```

## 三、Session/Cookie 方案的三个核心问题

### 问题一：水平扩展困难（最致命）

假设你的网站越来越火，一台服务器不够了，需要部署三台，用负载均衡分发请求：

```
          用户
           │
     负载均衡器
    /     │     \
服务器A  服务器B  服务器C
```

用户在**服务器A**上登录，Session 存在 A 的内存里。

下一个请求被负载均衡打到了**服务器B**，B 的内存里没有这个 Session → **用户被迫重新登录**。

解决方案及代价：

| 方案 | 做法 | 代价 |
|---|---|---|
| 粘性会话（Sticky Session） | 同一用户的请求永远打到同一台服务器 | 失去负载均衡的意义，一台挂了所有用户掉线 |
| Session 共享（Redis/数据库） | 把 Session 存到所有服务器都能访问的中心存储 | 增加架构复杂度，每次请求多一次 Redis 查询 |
| Session 复制 | 每台服务器都保存全量 Session | 内存占用巨大，网络带宽浪费 |

**这就是为什么 JWT 对分布式系统更友好**：JWT 是自包含的（用户信息直接在令牌里），每台服务器只需要验签就能知道是谁，完全不需要共享状态。

### 问题二：服务端有存储压力

每个登录用户都在服务器上占用一条 Session 记录。100 万个活跃用户 = 100 万条 Session 记录。

用内存存：占内存
用 Redis 存：多一次网络查询 + Redis 也需要维护

JWT 方案：服务器不存任何东西，只有一对 RSA 公私钥，大小固定不变。

### 问题三：跨域使用复杂

Cookie 有同源策略限制。如果你的前端在 `zhiguang.cn`，API 在 `api.zhiguang.cn`，Cookie 默认不会跨子域携带（需要额外配置 `domain=.zhiguang.cn`）。//这里说的不对
更麻烦的是：如果 App（iOS/Android）想调用同一套 API，App 没有浏览器，不支持 Cookie 的自动携带机制——需要手动模拟 Cookie 行为，非常麻烦。

JWT 只是一个字符串，放在 `Authorization: Bearer xxx` 请求头里，HTTP 头在任何端（浏览器、App、小程序、服务间调用）都支持，天然跨端。

## 四、JWT 方案：状态存客户端令牌里

### 完整工作流程

```
第一步：用户登录
┌──────────────────────────────────────────────────────────────┐
│  浏览器/App                      服务器                        │
│                                                               │
│  POST /login                                                  │
│  { username, password } ────────►  验证密码成功              │
│                                                               │
│                                    用私钥签发 JWT：            │
│                                    Header.Payload.Signature   │
│                                    Payload 包含：{            │
│                                      userId: 10001,           │
│                                      exp: 时间戳+15分钟        │
│                                    }                          │
│                                    服务器不存任何东西！         │
│                                                               │
│  ◄────────────────────────────── 响应体 JSON                  │
│  { accessToken: "eyJ...", refreshToken: "eyJ..." }            │
│  （前端自己存到 localStorage 或内存）                         │
└──────────────────────────────────────────────────────────────┘

第二步：后续每个请求
┌──────────────────────────────────────────────────────────────┐
│  浏览器/App                      服务器A / B / C              │
│                                                               │
│  GET /api/orders                                              │
│  Authorization: Bearer eyJ... ──►                            │
│  （前端代码主动加这个请求头）                                 │
│                                                               │
│                                    用公钥验证签名              │
│                                    → 签名有效                  │
│                                    → 检查 exp 未过期           │
│                                    → 从 Payload 取 userId=10001│
│                                    → 不需要查任何数据库！       │
│                                                               │
│  ◄────────────────────────────── 返回张三的订单数据           │
└──────────────────────────────────────────────────────────────┘
```

**关键特征**：
- 服务端**零存储**（只需要一对密钥）
- 用户信息直接编码在令牌里（自包含）
- 验证是纯内存运算（RSA 验签），无网络 I/O
- 前端需要主动管理令牌（存储、携带、刷新）

## 五、两种方案的全面对比

### 5.1 架构层面

| 维度 | Session/Cookie | JWT |
|---|---|---|
| 状态存储位置 | 服务端（内存/Redis/DB） | 客户端（localStorage/内存） |
| 服务端存储压力 | 随用户数线性增长 | 零（只有固定大小的密钥） |
| 水平扩展 | 需要 Session 共享方案 | 天然支持，每台服务器独立验证 |
| 验证方式 | 查 Session 存储（网络 I/O） | 本地验签（纯内存运算） |
| 验证性能 | ~0.5~2ms（Redis 查询） | ~0.1ms（RSA 运算） |

### 5.2 功能层面

| 维度 | Session/Cookie | JWT |
|---|---|---|
| 即时撤销会话 | ✅ 删除 Session 即可立即失效 | ❌ 需要额外的黑名单/白名单机制 |
| 跨端支持 | ❌ Cookie 是浏览器特性，App 不原生支持 | ✅ 任何能发 HTTP 请求的端都支持 |
| 跨域使用 | ❌ 需要额外配置，复杂 | ✅ 天然支持（只是个 HTTP 头） |
| 存储容量 | 无限制（服务端存任意多数据） | 有限制（令牌字符串不能太长，建议 < 4KB） |
| 修改用户信息立即生效 | ✅ 修改 Session 数据即可 | ❌ 令牌已签发，信息固化到过期 |

### 5.3 安全层面

| 维度 | Session/Cookie | JWT |
|---|---|---|
| 令牌泄露损失 | sessionId 被盗 → 服务端删除 Session 立即失效 | AT 被盗 → 最多 15 分钟内可被利用 |
| CSRF 攻击风险 | ❌ Cookie 自动携带，CSRF 攻击容易实施（需要 CSRF 保护） | ✅ 需要 JS 主动读取携带，恶意网站 JS 无法读取其他域的 localStorage |
| XSS 攻击风险 | ✅ HttpOnly Cookie 无法被 JS 读取 | ❌ localStorage 可被 XSS 读取 |
| 服务端被攻击 | 攻击者可读取所有 Session 数据（含用户信息） | 攻击者只能读到加密存储（本项目 Redis 只存 jti，无完整令牌） |

## 六、一个重要的思维误区

**很多人认为"Cookie 就等于 Session"，这是错的。**

Cookie 只是一种**存储和传输机制**，它可以存任何东西：
- 存 sessionId → 这是 Session/Cookie 方案
- 存 JWT 字符串 → 这是 JWT in Cookie 方案（也是可以的）

```
三种常见组合：

方案1：Session + Cookie（传统 Web）
  服务端：存 Session 数据
  Cookie：存 sessionId（一串随机 UUID）
  浏览器：自动携带

方案2：JWT + localStorage（本项目，现代 SPA / App）
  服务端：不存任何东西
  localStorage：存 JWT 字符串
  前端代码：手动加 Authorization 头

方案3：JWT + HttpOnly Cookie（最安全的 JWT 用法）
  服务端：不存任何东西
  HttpOnly Cookie：存 JWT 字符串（JS 无法读取，防 XSS）
  浏览器：自动携带（需要配合 CSRF 保护）
```

方案3（JWT + HttpOnly Cookie）融合了两种方案的优点：JWT 的无状态 + Cookie 的 XSS 防护，是目前安全性最高的前端认证方案，但实现复杂度也最高。

## 七、本项目为什么选 JWT + localStorage

本项目选择 JWT + 响应体下发（前端存 localStorage）的原因：

**1. 面向多端**：知识平台未来可能有 Web、App（iOS/Android）、小程序多端。JWT 作为字符串，各端处理方式一致；Cookie 方案在 App 端需要额外处理。

**2. 无状态扩展**：服务器只需要 RSA 公钥就能验证，不需要 Redis Session，水平扩展简单。

**3. CSRF 风险低**：使用 `Authorization` 头而不是 Cookie，天然防 CSRF，可以关闭 CSRF 保护（`csrf.disable()`）简化配置。

**4. 以 RT 白名单弥补不可撤销的缺陷**：JWT 的最大弱点是不能即时撤销。本项目通过 RT 白名单（Redis）解决：虽然 AT 不可即时撤销，但 AT 只有 15 分钟；RT 可以通过撤销白名单实现即时失效（下次刷新时生效）。

---

## 八、什么情况下应该选 Session/Cookie

JWT 不是银弹，以下场景 Session/Cookie 反而更合适：

**1. 需要即时踢出用户**：如发现账号异常需要立刻失效。Session 删一条记录即可；JWT 要等 AT 自然过期（15 分钟）。

**2. 纯浏览器 Web 应用、不需要跨端**：Cookie 由浏览器自动处理，前端代码更简单（不需要手动管理令牌存储、刷新逻辑、携带 Header 等）。

**3. 服务端需要存储会话数据**：如购物车（一些传统实现把购物车存 Session）、复杂的服务端渲染状态等。

**4. 极强安全性要求 + 不在意扩展难度**：金融系统、政务系统，每次操作都需要服务端验证当前 Session 是否仍在有效状态。

## 九、总结

```
Session/Cookie（传统 Web）         JWT（现代分布式 / 多端）
─────────────────────────────────────────────────────────────
✅ 即时撤销                       ✅ 无状态，零存储压力
✅ HttpOnly Cookie 防 XSS         ✅ 天然防 CSRF
✅ 用户信息可随时更新              ✅ 水平扩展无痛
❌ 水平扩展需要 Session 共享       ✅ 跨端（Web/App/小程序）统一
❌ 不支持多端                     ❌ 不可即时撤销（靠短有效期弥补）
❌ 随用户增长存储压力大            ❌ XSS 可读取 localStorage
```

> 两种方案各有适用场景，没有绝对好坏。本项目选 JWT，核心原因是**多端支持** + **无状态水平扩展** + **开发成本低**，并用 RT 白名单机制弥补了 JWT 不可即时撤销的先天缺陷。
