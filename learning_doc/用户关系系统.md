# 用户关系系统详解

> 实现关注/取关功能，采用**一主多从 + 事件驱动**架构。关注表作为"主"，粉丝表、计数 SDS、Redis ZSet 列表缓存都作为"伪从"，通过 Canal 订阅 Outbox 表 binlog → Kafka 异步驱动，实现最终一致性。

## 二、整体架构：一主多从 + 事件驱动

```
                    ┌──────────────────────────┐
                    │   用户发起关注请求         │
                    └──────────────┬───────────┘
                                   │ @Transactional（同一事务）
                    ┌──────────────▼───────────┐
                    │    1. INSERT following    │  主表
                    │    2. INSERT outbox       │  发件箱
                    └──────────────────────────┘
                                   │
                            MySQL binlog
                                   │
                    ┌──────────────▼───────────┐
                    │        Canal Server       │
                    │  监听 outbox 表变更        │
                    └──────────────┬───────────┘
                                   │ 推送到 Kafka
                    ┌──────────────▼───────────┐
                    │    Kafka Topic: outbox    │
                    └──────────────┬───────────┘
                                   │ 消费（CanalOutboxConsumer）
                    ┌──────────────▼───────────┐
                    │   RelationOutboxProcessor │
                    │  ┌─────────────────────┐ │
                    │  │  UPDATE follower 表  │ │  伪从1：粉丝表
                    │  │  UPDATE Redis ZSet   │ │  伪从2：列表缓存
                    │  │  UPDATE 用户计数 SDS │ │  伪从3：计数快照
                    │  └─────────────────────┘ │
                    └──────────────────────────┘
```

**关键优势**：关注操作的核心写（following 表）与派生写（粉丝表/缓存/计数）解耦，关注操作响应速度极快，不受派生写延迟影响。

## 三、关注写流程

### 3.1 follow（关注）

```
POST /api/v1/relations/follow
{toUserId}
  │
  ▼
RelationServiceImpl.follow(fromUserId, toUserId)
  │
  ├─ 1. 令牌桶限流（Lua 脚本）
  │      Key: rl:follow:{fromUserId}
  │      capacity=100, rate=1（每秒补充1个令牌）
  │      令牌不足（0）→ 直接返回 false（被限流）
  │
  ├─ 2. @Transactional 事务边界内：
  │      ├─ mapper.insertFollowing(id, fromUserId, toUserId, rel_status=1)
  │      │    使用 ON DUPLICATE KEY UPDATE，支持"重新关注"幂等
  │      └─ outboxMapper.insert(outId, "following", id, "FollowCreated", payload)
  │           payload = JSON{type:"FollowCreated", from, to, followId}
  │
  └─ 3. 事务提交后：Canal 捕获 outbox 表新增行 → Kafka
```

### 3.2 unfollow（取消关注）

```
POST /api/v1/relations/unfollow
{toUserId}
  │
  ▼
RelationServiceImpl.unfollow(fromUserId, toUserId)
  │
  ├─ 1. @Transactional：
  │      ├─ mapper.cancelFollowing(fromUserId, toUserId)
  │      │    UPDATE following SET rel_status=0 WHERE from=? AND to=?
  │      └─ outboxMapper.insert(..., "FollowCanceled", payload)
  │
  └─ 2. 事务提交后：同样通过 Canal → Kafka → 异步处理派生写
```

### 3.3 Lua 令牌桶限流

```lua
-- TOKEN_BUCKET_LUA
local key = KEYS[1]
local capacity = tonumber(ARGV[1])  -- 100
local rate = tonumber(ARGV[2])      -- 1（每秒补充1令牌）
local now = redis.call('TIME')[1]   -- 当前秒级时间戳

local last = redis.call('HGET', key, 'last')
local tokens = redis.call('HGET', key, 'tokens')
if not last then
    last = now
    tokens = capacity  -- 首次初始化：满桶
end

-- 根据时间差计算补充令牌
local elapsed = now - last
local add = elapsed * rate
tokens = math.min(capacity, tokens + add)

-- 令牌不足
if tokens < 1 then
    redis.call('HSET', key, 'last', now, 'tokens', tokens)
    return 0  -- 被限流
end

-- 消耗1令牌
tokens = tokens - 1
redis.call('HSET', key, 'last', now, 'tokens', tokens)
redis.call('PEXPIRE', key, 60000)  -- 60秒后自动清理
return 1  -- 允许通过
```

## 四、Canal + Outbox 事件消费

### 4.1 Canal 消息格式

Canal 捕获 MySQL binlog 后，将变更推送到 Kafka，消息格式如下：

```json
{
  "database": "zhiguang",
  "table": "outbox",
  "type": "INSERT",
  "data": [
    {
      "id": "xxx",
      "aggregate_type": "following",
      "aggregate_id": "123",
      "type": "FollowCreated",
      "payload": "{\"type\":\"FollowCreated\",\"from\":456,\"to\":789,\"followId\":123}",
      "created_at": "2024-01-01 12:00:00"
    }
  ]
}
```

### 4.2 OutboxMessageUtil 解析

```java

    // 解析 Canal JSON → 过滤 table/type → 提取 data 数组
}
```

### 4.3 CanalOutboxConsumer（Kafka Consumer）

```
监听 Kafka Topic: binlog-outbox
  │
  ├─ 1. extractRows → 解析 outbox 行
  ├─ 2. 提取 aggregate_type + type + payload
  └─ 3. 路由到 RelationOutboxProcessor
```

### 4.4 RelationOutboxProcessor（业务处理）

```
FollowCreated 事件：
  ├─ 1. 幂等检查（follower 表中已有记录则跳过）
  ├─ 2. INSERT INTO follower(toUserId, fromUserId) ON DUPLICATE KEY UPDATE
  ├─ 3. Redis ZSet 更新
  │      ZADD uf:flws:{fromUserId} score={createdAt} member={toUserId}
  │      ZADD uf:fans:{toUserId}   score={createdAt} member={fromUserId}
  └─ 4. 用户计数 SDS 更新
         incrementFollowings(fromUserId, +1)
         incrementFollowers(toUserId, +1)

FollowCanceled 事件：
  ├─ 1. UPDATE follower SET rel_status=0
  ├─ 2. ZREM uf:flws:{fromUserId} {toUserId}
  │     ZREM uf:fans:{toUserId}   {fromUserId}
  └─ 3. 用户计数 SDS 更新（-1）
```

## 五、关注/粉丝列表读取流程

### 5.1 三级缓存设计

```
请求：获取 userId 的关注列表
  │
  ├─ L1: Caffeine 本地缓存（仅大V用户）
  │       key: userId, value: List<Long>（前500个关注ID）
  │       TTL: 10分钟
  │       hitRate: 对大V而言极高
  │
  ├─ L2: Redis ZSet 缓存
  │       key: uf:flws:{userId}
  │       score: 关注时间戳（毫秒）
  │       TTL: 2小时（回填后设置）
  │       支持两种分页：
  │         - 偏移分页：ZREVRANGE key offset limit
  │         - 游标分页：ZREVRANGEBYSCORE key max -inf LIMIT 0 limit
  │
  └─ L3: MySQL（DB 回填）
          mapper.listFollowingRows(userId, limit, offset)
          回填后写入 Redis ZSet + 设置 TTL
```

### 5.2 偏移分页流程（following / followers）

```java
getListWithOffset(key, offset, limit, rowsFetcher, ...)
  │
  ├─ 1. 本地缓存命中（大V）？→ 返回对应切片
  ├─ 2. Redis ZSet 命中？→ ZREVRANGE key offset (offset+limit-1)
  └─ 3. DB 回填：
         ├─ rowsFetcher(limit+offset)（取足够多行）
         ├─ fillZSet：ZADD key score member（时间戳为分值）
         ├─ EXPIRE key 2h
         ├─ 若为大V：maybeUpdateTopCache（缓存前500个到 Caffeine）
         └─ 重查 Redis ZSet 返回
```

### 5.3 游标分页流程（followingCursor / followersCursor）

```java
getListWithCursor(key, limit, cursor, ...)
  │
  ├─ cursor == null → max = +∞（第一页）
  ├─ cursor != null → max = cursor（上一页末条时间戳）
  ├─ ZREVRANGEBYSCORE key max -inf LIMIT 0 limit → 命中则返回
  └─ 未命中 → DB 回填 → EXPIRE → 重查返回
```

**游标分页优势**：不依赖 offset，不会随翻页增加查询成本，且在列表插入新关注时不会导致分页重复/遗漏（以时间戳为游标，新关注在前）。

## 六、大V（Big V）识别与本地缓存

### 6.1 大V 判断

```java
private boolean isBigV(long userId) {
    byte[] raw = redis.execute(...);  // GET ucnt:{userId}
    // 读取 SDS 第3个字段（offset=8）= followers 数
    long followers = readInt32BE(raw, 8);
    return followers >= 500_000L;  // 粉丝数 >= 50万
}
```

### 6.2 大V 优化策略

大V（如明星、大博主）的关注列表会被大量用户并发查询：
- 回填时缓存前 500 个粉丝到 Caffeine（`fansTopCache`）
- 后续请求直接从本地内存返回，无需 Redis 网络 IO
- TTL 10 分钟，过期后自动从 Redis 重新加载

## 七、关系状态查询

```java
relationStatus(userId, otherUserId) → {
    following:  isFollowing(userId, otherUserId),   // 我是否关注了对方
    followedBy: isFollowing(otherUserId, userId),   // 对方是否关注了我
    mutual:     following && followedBy              // 互相关注
}
```

三态关系：**关注中 / 被关注 / 互粉**，直接查 following 表（B-Tree 索引），不走缓存。

## 八、数据库设计

### 8.1 following 表（关注主表）

```sql
CREATE TABLE following (
    id          BIGINT PRIMARY KEY,
    from_user_id BIGINT NOT NULL,      -- 发起关注者
    to_user_id   BIGINT NOT NULL,      -- 被关注者
    rel_status   TINYINT DEFAULT 1,    -- 1=有效, 0=已取消
    created_at   TIMESTAMP NOT NULL,
    UNIQUE KEY uk_from_to (from_user_id, to_user_id)
)
```

使用 `ON DUPLICATE KEY UPDATE rel_status=1` 支持重新关注幂等。

### 8.2 follower 表（粉丝表）

由 Canal Outbox 事件异步维护，结构与 following 表对称，以 `to_user_id` 为主视角。

### 8.3 outbox 表（事件发件箱）

```sql
CREATE TABLE outbox (
    id             BIGINT PRIMARY KEY,
    aggregate_type VARCHAR(64),   -- 'following'
    aggregate_id   BIGINT,        -- 关注记录 ID
    type           VARCHAR(64),   -- 'FollowCreated' / 'FollowCanceled'
    payload        TEXT,          -- JSON 事件载荷
    created_at     TIMESTAMP
)
```

## 十、设计亮点与学习要点

1. **Outbox 模式（事务性发件箱）**：在同一 MySQL 事务中同时写业务表和 Outbox 表，保证"关注成功"与"事件发出"的原子性，Canal 订阅 binlog 确保事件不丢失
2. **一主多从架构**：following 表为权威来源（主），follower 表/ZSet/SDS 均为派生副本（从），派生写允许短暂延迟，不阻塞主写
3. **ZSet 时间戳分值**：以关注时间戳作为 ZSet 分值，自然实现按时间倒序排列，同时支持基于时间的游标分页
4. **大V 优化**：本地 Caffeine 缓存大V 粉丝 Top500，解决热点用户的关注列表高并发读问题
5. **令牌桶限流（Lua）**：防止恶意用户频繁关注/取关刷数据；Lua 脚本保证令牌桶读写原子性
6. **Canal + Kafka 解耦**：MySQL binlog → Canal → Kafka → Consumer，业务代码不直接操作 Canal，通过 Kafka 解耦后可以有多个独立消费者（搜索索引更新、通知推送等）
7. **幂等消费**：Outbox 消费者对每条事件做幂等检查（follower 表 ON DUPLICATE KEY），即使 Kafka 重复投递也不会产生脏数据
