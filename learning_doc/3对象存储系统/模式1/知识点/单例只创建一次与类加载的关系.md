# 单例"只创建一次"与类加载的关系

> "程序启动时创建一次"这句话涉及到两个层次：JVM 的类加载 和 对象实例化。两者完全不同，但又密切相关。本文把这两件事讲清楚，并说明 Spring 单例 Bean 到底是靠哪个机制实现"只创建一次"的。

---

## 一、先区分两个完全不同的事情

很多人会把这两件事混为一谈：

```
事情一：类加载（Class Loading）
  → "OSSClient 这个类的字节码"被 JVM 加载进内存
  → 结果：JVM 知道了 OSSClient 这个类的定义（有哪些字段、方法）
  → 此时还没有任何 OSSClient 对象存在

事情二：对象实例化（Object Instantiation）
  → 执行 new OSSClientBuilder().build(...)
  → 结果：在堆内存里创建了一个具体的 OSSClient 实例
  → 此时才真正有了一个可以用的 OSSClient 对象
```

**类加载 ≠ 对象创建。** 类只需要加载一次（JVM 保证），但对象可以 new 无数次，也可以只 new 一次（单例）。

---

## 二、JVM 类加载：发生了什么，发生在什么时候

### 2.1 类加载的时机

JVM 采用**懒加载（Lazy Loading）**策略：**一个类在第一次被用到时才加载**，而不是程序启动时就把所有类都加载进来。

"第一次被用到"包括：
- 创建这个类的实例（`new OSSClient()`）
- 访问这个类的静态字段（`OSSClient.SOME_STATIC_FIELD`）
- 调用这个类的静态方法（`OSSClient.staticMethod()`）
- 这个类是程序的入口类（`main` 方法所在类）

### 2.2 类加载做了什么

```
第一步：加载（Loading）
  ClassLoader 从 .jar 文件中找到 OSSClient.class 文件
  读取字节码，放入 JVM 的方法区（Method Area）
  → 方法区里现在有了 OSSClient 类的结构描述

第二步：链接（Linking）
  验证：字节码格式是否合法
  准备：为静态变量分配内存，赋默认值（0/null/false）
  解析：把符号引用（类名字符串）替换为直接引用（内存地址）

第三步：初始化（Initialization）
  执行静态初始化块（static {}）和静态变量赋值
  例：static final String DEFAULT_ENDPOINT = "oss-cn-beijing...";
  → 这时静态变量才有了真正的值
```

**关键结论**：类加载完成后，**只是把类的定义放进了 JVM**，还没有任何对象实例存在于堆内存中。

### 2.3 类加载与单例的关系

传统的静态单例确实依赖类加载机制：

```java
// 饿汉式单例：在类初始化阶段创建实例
public class OssClientHolder {
    // static final 变量在类初始化时赋值
    // 类初始化是类加载的第三步，JVM 保证只执行一次
    private static final OssClientHolder INSTANCE = new OssClientHolder();

    private OssClientHolder() { /* ... */ }

    public static OssClientHolder getInstance() {
        return INSTANCE;
    }
}
```

这里 `private static final OssClientHolder INSTANCE = new OssClientHolder()` 的赋值，发生在**类初始化阶段**（类加载第三步）。

JVM 规范保证：**类初始化在整个 JVM 中只执行一次**，且是线程安全的（有锁保护）。

所以，**"程序启动时只创建一次"这个说法中，"只一次"的保证来自 JVM 对类初始化的保证**——类初始化只发生一次，静态变量的赋值自然也只执行一次。

### 2.4 静态单例在初始化阶段究竟是如何创建的？对象存在哪里？

这是理解单例内存模型最容易混淆的地方，需要把"**引用存在哪**"和"**对象本体存在哪**"分开来看。

#### 第一步：类加载的"准备"阶段

```
类加载 → 链接 → 准备阶段：
  JVM 在方法区（Method Area）中为 OssClientHolder 这个类分配空间，
  存放类的静态变量描述，并为静态变量赋默认值（null）：

  方法区中的 OssClientHolder 类信息：
  ┌─────────────────────────────────────────┐
  │ 类名: OssClientHolder                   │
  │ 静态字段 INSTANCE: null（默认值，占位）  │  ← 此时只是一个 null 引用
  │ 方法表: getInstance(), 构造方法...       │
  └─────────────────────────────────────────┘
```

注意：**此时对象还没有被创建，方法区里只有一个 `null` 引用作为占位。**

#### 第二步：类加载的"初始化"阶段

```
类加载 → 链接 → 初始化阶段：
  JVM 执行类的 <clinit>() 方法（类的静态初始化方法，编译器自动生成）
  <clinit>() 内容 = 所有静态变量的赋值语句 + static{} 块

  执行 INSTANCE = new OssClientHolder() 时：
    1. JVM 在【堆内存（Heap）】中分配一块内存，创建 OssClientHolder 对象
    2. 调用构造方法，初始化对象的字段
    3. 把这个对象在堆中的内存地址（引用）赋值给方法区中的 INSTANCE 字段
```

执行完毕后，内存布局如下：

```
方法区（Method Area）：
┌─────────────────────────────────────────────────┐
│ 类名: OssClientHolder                            │
│ 静态字段 INSTANCE: → 0x1a2b3c（堆内存地址）     │  ← 引用，指向堆
│ 方法表: getInstance()...                         │
└─────────────────────────────────────────────────┘
                           │
                           │ 指向
                           ↓
堆内存（Heap）：
┌──────────────────────────────┐
│ OssClientHolder 对象实例      │  ← 对象本体在这里！
│ 地址: 0x1a2b3c               │
│ 对象头（hashcode, gc info...）│
│ ossClient 字段: → ...        │
└──────────────────────────────┘
```

#### 结论：引用 vs 对象本体，分别在哪

| 存放的内容 | 存放位置 | 说明 |
|-----------|---------|------|
| **静态变量 `INSTANCE`（引用）** | 方法区 / 元空间（Metaspace） | 只是一个 8 字节的内存地址，指向堆中的对象 |
| **`OssClientHolder` 对象本体** | 堆内存（Heap） | 真正的对象数据在这里，GC 负责管理 |

> ⚠️ **常见误解**："静态变量在方法区，所以对象也在方法区"——这是错的。
> 静态变量本身（`INSTANCE` 这个引用槽）在方法区，但引用指向的**对象实例**永远在堆里。
> 任何通过 `new` 关键字创建的对象，无论是普通实例还是单例，本体都在堆内存中。

#### 为什么 JVM 能保证只创建一次

JVM 规范规定：**`<clinit>()` 方法的执行是互斥的**。在多线程环境下，如果两个线程同时触发同一个类的初始化，JVM 会用一把内置的初始化锁（InitializationLock）保证只有一个线程执行 `<clinit>()`，另一个线程阻塞等待。等第一个线程执行完毕，第二个线程进来时发现类已经初始化完成，直接跳过。

```
线程 A 和线程 B 同时第一次使用 OssClientHolder：

线程 A：拿到初始化锁，执行 <clinit>()，创建对象，INSTANCE 被赋值
线程 B：等待锁
线程 A：释放锁
线程 B：拿到锁，检查发现类已经初始化完毕，直接退出，不再执行 <clinit>()

结果：对象只被创建了一次，INSTANCE 只被赋值了一次
```

这就是为什么**饿汉式静态单例天然是线程安全的**，不需要额外加 `synchronized`。

## 三、Spring 单例 Bean：不依赖类加载，靠容器控制

Spring 的单例 Bean 和上面的静态单例不同，它**不依赖类加载机制来保证唯一性**，而是靠 **Spring 容器自己的逻辑**来实现。

### 3.1 Spring 容器的本质

Spring 容器（`ApplicationContext`）在内部维护了一个 Map：

```java
// Spring 容器内部（简化示意）
Map<String, Object> singletonObjects = new ConcurrentHashMap<>();
// key：Bean 的名字（如 "chatClient"）
// value：Bean 的实例对象
```

### 3.2 Spring 单例 Bean 的创建时机

Spring Boot 启动时，会扫描所有 `@Bean`、`@Component`、`@Service` 等注解，然后按顺序**实例化**所有单例 Bean，把它们放进 `singletonObjects` 这个 Map 里：

```
Spring Boot 启动过程（简化）：

  1. main() 方法执行 SpringApplication.run()

  2. Spring 扫描所有配置类和组件类

  3. 对每个单例 Bean：
     a. 调用构造方法或 @Bean 方法，创建对象  ← 对象实例化在这里发生
     b. 注入依赖（@Autowired）
     c. 调用初始化方法（@PostConstruct）
     d. 把创建好的对象放入 singletonObjects Map

  4. 启动完成，开始接受 HTTP 请求

具体到 ChatClient 的创建：
  → LlmConfig.chatClient() 方法被调用一次
  → 返回的 ChatClient 实例放入 singletonObjects
  → key = "chatClient"，value = 那个 ChatClient 对象
```

### 3.3 后续注入时发生了什么

```java
@Service
@RequiredArgsConstructor
public class RagQueryService {
    private final ChatClient chatClient;  // 这里的注入
}
```

`@Autowired` / `@RequiredArgsConstructor` 注入时，Spring 做的事是：

```
不是创建新对象！
而是：从 singletonObjects Map 里取出 key="chatClient" 对应的那个对象，
      赋值给 RagQueryService 的 chatClient 字段。

所以：
  RagQueryService 里的 chatClient ─────────┐
                                           ↓
  KnowPostDescriptionServiceImpl 里的 chatClient ← 同一个对象
                                           ↑
  （singletonObjects 里只有一个 ChatClient 实例）
```

### 3.4 Spring 如何保证"只创建一次"

Spring 在创建 Bean 之前会先查 `singletonObjects`：

```java
// Spring 内部的 getBean 逻辑（简化）
public Object getBean(String name) {
    // 先从缓存里查
    Object existing = singletonObjects.get(name);
    if (existing != null) {
        return existing;  // 已经创建过，直接返回，不再创建
    }

    // 没有则创建，创建完立刻放入缓存
    Object newBean = createBean(name);
    singletonObjects.put(name, newBean);
    return newBean;
}
```

这就是 Spring 单例的"只创建一次"：**不是语言层面的保证，而是容器逻辑的保证——在创建之前先查缓存，有了就不再创建**。

## 四、两种"只创建一次"的对比

| 维度 | 静态单例（类加载机制） | Spring 单例 Bean（容器机制） |
|------|---------------------|--------------------------|
| **保证来源** | JVM 类初始化只执行一次 | Spring 容器查 Map 缓存 |
| **创建时机** | 类被第一次使用时（懒加载）或程序启动时（饿汉式） | Spring 容器启动时 |
| **线程安全保证** | JVM 类初始化有内置锁 | Spring 用 `ConcurrentHashMap` + DCL |
| **能否绕开** | 几乎不能（private 构造） | 可以在容器外 `new` 出多个实例 |
| **依赖类加载** | 是（静态变量赋值在类初始化阶段） | 只是间接依赖（任何对象创建都需要先加载类） |

## 五、把整个流程串起来

以本项目的 `ChatClient` 为例，从 JVM 启动到可以使用 `chatClient`，完整经历了：

```
步骤一：JVM 类加载（懒加载，首次使用时触发）
  Spring 扫描到 LlmConfig 时，JVM 加载 LlmConfig.class
  Spring 处理到 ChatClient 时，JVM 加载 ChatClient.class
  → 方法区里有了类定义，但还没有任何 ChatClient 对象

步骤二：Spring 容器初始化（程序启动时，SpringApplication.run() 内部）
  Spring 发现 LlmConfig 里有 @Bean public ChatClient chatClient(...)
  Spring 调用这个方法一次：
    return ChatClient.builder(chatModel).build();
  → 堆内存里创建了一个 ChatClient 对象（实例化）
  → 这个对象放入 singletonObjects Map：key="chatClient"

步骤三：依赖注入（Bean 创建时）
  Spring 创建 RagQueryService 时，发现需要注入 ChatClient
  从 singletonObjects 取出 key="chatClient" 的对象
  赋值给 RagQueryService.chatClient 字段
  → 没有新建对象，只是"取"

步骤四：HTTP 请求到来（程序运行时）
  RagQueryService.streamAnswerFlux() 被调用
  使用的 chatClient 就是步骤二里创建的那个对象
  → 10,000 次请求，使用的都是同一个对象
```

**总结**：
- 类加载（步骤一）发生在首次使用类时，JVM 保证每个类只加载一次
- 对象创建（步骤二）发生在 Spring 容器启动时，Spring 容器保证单例 Bean 只创建一次
- "程序启动时创建一次"说的是步骤二，不是步骤一；步骤一是类加载，步骤二才是对象实例化

## 六、一句话总结

**类加载和对象创建是两件事**：类加载是把类的定义放进 JVM（JVM 保证每个类只加载一次），对象创建是在堆内存里 `new` 出实例（可以创建任意多个）。

"Spring 单例 Bean 只在程序启动时创建一次"靠的是 **Spring 容器的 Map 缓存机制**，不是类加载机制（虽然类加载是对象创建的前提）。静态单例则直接利用了"类初始化只执行一次"这个 JVM 保证，把实例创建绑定在类初始化阶段。
