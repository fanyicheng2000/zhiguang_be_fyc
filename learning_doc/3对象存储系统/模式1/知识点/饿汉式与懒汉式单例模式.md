# 饿汉式与懒汉式单例模式

> 单例模式有两种经典实现，区别只在一件事上：**什么时候创建那个唯一的实例**。

---

## 一、核心区别一句话

```
饿汉式：类一加载就立刻创建实例（迫不及待，很"饿"）
懒汉式：第一次使用时才创建实例（能拖就拖，很"懒"）
```

---

## 二、饿汉式（Eager Initialization）

### 代码

```java
public class EagerSingleton {

    // 类加载时就创建好实例，赋值给静态变量
    private static final EagerSingleton INSTANCE = new EagerSingleton();

    // 私有构造，外部无法 new
    private EagerSingleton() {
        System.out.println("EagerSingleton 实例被创建");
    }

    public static EagerSingleton getInstance() {
        return INSTANCE;  // 直接返回，永远不为 null
    }
}
```

### 什么时候创建

`EagerSingleton` 类被加载时（类加载的第三步：初始化阶段），静态变量 `INSTANCE` 被赋值，对象创建。

```
程序启动，首次访问 EagerSingleton（比如调用 getInstance()）
  → JVM 触发类加载
  → 类初始化阶段：执行 INSTANCE = new EagerSingleton()
  → 对象已存在
  → 返回 INSTANCE
```

### 特点

| | 说明 |
|--|--|
| **线程安全** | ✅ 天然安全。JVM 类初始化有内置锁（InitializationLock），保证只执行一次，不需要你写 `synchronized` |
| **创建时机** | 类加载时，不管你用不用 |
| **内存占用** | 如果这个单例对象很重但你一直没用到，内存白白被占着 |
| **代码简洁** | ✅ 最简单，没有并发问题 |

## 三、懒汉式（Lazy Initialization）

### 3.1 最简单的懒汉式（线程不安全）

```java
public class LazySingleton {

    // 先不创建，null 占位
    private static LazySingleton instance = null;

    private LazySingleton() {
        System.out.println("LazySingleton 实例被创建");
    }

    public static LazySingleton getInstance() {
        if (instance == null) {         // 第一次调用时才创建
            instance = new LazySingleton();
        }
        return instance;
    }
}
```

**什么时候创建**：第一次有人调用 `getInstance()` 时。

**问题**：在多线程环境下不安全——

```
线程 A 和线程 B 同时第一次调用 getInstance()：

线程 A：if (instance == null)  → true，准备创建
线程 B：if (instance == null)  → true，也准备创建（A 还没创建完）

结果：两个线程都进入了 if 块，创建了两个实例
     → 单例被破坏！
```

### 3.2 加锁的懒汉式（线程安全，但性能差）

```java
public class SynchronizedLazySingleton {

    private static SynchronizedLazySingleton instance = null;

    private SynchronizedLazySingleton() {}

    // 整个方法加锁：保证同一时刻只有一个线程进入
    public static synchronized SynchronizedLazySingleton getInstance() {
        if (instance == null) {
            instance = new SynchronizedLazySingleton();
        }
        return instance;
    }
}
```

**问题**：`synchronized` 加在整个方法上，即使实例已经创建好了，后续每次 `getInstance()` 都要竞争锁，性能很差。

### 3.3 双重检查锁（DCL，推荐的懒汉式写法）

```java
public class DCLSingleton {

    // volatile 关键字必须加！原因见下文
    private static volatile DCLSingleton instance = null;

    private DCLSingleton() {}

    public static DCLSingleton getInstance() {
        if (instance == null) {              // 第一次检查（无锁，快）
            synchronized (DCLSingleton.class) {
                if (instance == null) {      // 第二次检查（有锁，防并发）
                    instance = new DCLSingleton();
                }
            }
        }
        return instance;  // 实例已存在时，完全不加锁，直接返回
    }
}
```

**为什么要检查两次**：

```
没有第二次检查的问题：
  线程 A 和 B 都通过了第一次 if (instance == null)
  线程 A 先拿到锁，创建了实例，释放锁
  线程 B 拿到锁，此时没有第二次检查 → 又创建了一次！

有了第二次检查：
  线程 B 拿到锁后，再检查一次 instance == null
  发现 A 已经创建好了，instance 不为 null → 直接返回，不再创建
```

**为什么必须加 `volatile`**：

```
new DCLSingleton() 这条语句，JVM 实际执行 3 步：
  步骤 1：在堆上分配内存
  步骤 2：调用构造方法，初始化对象
  步骤 3：把内存地址赋值给 instance 变量

JVM 和 CPU 为了性能可能重排序，变成：
  步骤 1 → 步骤 3 → 步骤 2（先赋地址，后初始化）

如果 A 执行了步骤 1 和 3，但还没执行步骤 2（对象未初始化完）
此时 B 进来，第一次检查：instance != null → 直接返回
B 拿到的是一个未初始化完成的对象！→ 使用时 NullPointerException

volatile 禁止指令重排序，保证步骤 1→2→3 严格按顺序执行。
```

### 3.4 静态内部类（最优雅的懒汉式）

```java
public class HolderSingleton {

    private HolderSingleton() {}

    // 静态内部类：只有在被引用时，这个类才会被加载
    private static class Holder {
        // Holder 类加载时，INSTANCE 被创建（利用饿汉式的类加载保证）
        private static final HolderSingleton INSTANCE = new HolderSingleton();
    }

    public static HolderSingleton getInstance() {
        return Holder.INSTANCE;  // 第一次调用时，Holder 类才被加载，INSTANCE 才被创建
    }
}
```

这种写法的精妙之处：
- **懒加载**：`Holder` 类只在 `getInstance()` 第一次被调用时才加载，INSTANCE 才被创建
- **线程安全**：利用 JVM 类初始化的内置锁，天然安全，不需要 `synchronized`
- **无性能损耗**：没有锁竞争，`getInstance()` 本身完全不加锁

## 四、三种写法的完整对比

| 写法 | 创建时机 | 线程安全 | 性能 | 代码复杂度 |
|------|---------|---------|------|----------|
| 饿汉式 | 类加载时 | ✅ 天然安全 | ✅ 无锁 | ✅ 最简单 |
| 懒汉式（无锁） | 首次使用时 | ❌ 不安全 | ✅ 无锁 | ✅ 简单 |
| 懒汉式（synchronized） | 首次使用时 | ✅ 安全 | ❌ 每次都锁 | ✅ 简单 |
| 双重检查锁（DCL） | 首次使用时 | ✅ 安全 | ✅ 只首次加锁 | ⚠️ 较复杂（需要 volatile）|
| 静态内部类 | 首次使用时 | ✅ 天然安全 | ✅ 无锁 | ✅ 简洁 |

## 五、怎么选

```
绝大多数情况下（包括 Spring 项目）：
  直接用饿汉式 或 把对象交给 Spring 管理（@Bean/@Component）

  原因：
  - Spring Bean 本来就是"程序启动时创建一次"，等价于饿汉式
  - 应用服务器内存充足，"启动时多占点内存"根本不是问题
  - 代码最简单，不用考虑并发问题

以下情况考虑懒汉式（静态内部类写法）：
  - 这个对象初始化非常耗时（比如要连接远程服务），
    且不是每次启动都会用到
  - 想让程序启动更快，把初始化延迟到真正使用时
```

## 六、Spring 单例 Bean 更像哪种

Spring 默认的单例 Bean（`scope="singleton"`）**更像饿汉式**：

```
Spring Boot 启动时（SpringApplication.run()）：
  → 扫描所有 @Bean/@Component
  → 立刻实例化所有单例 Bean，放入容器
  → 应用就绪

此后每次 @Autowired 注入：
  → 只是从容器 Map 里取，不再创建
```

不过 Spring 也支持懒加载：

```java
@Bean
@Lazy  // 加上这个注解 → 变成懒汉式，第一次被注入时才创建
public ChatClient chatClient(...) {
    return ChatClient.builder(chatModel).build();
}
```

默认不加 `@Lazy`，Spring 就是饿汉式行为。

---

## 七、一句话总结

```
饿汉式：简单、安全、启动时就创建，适合绝大多数场景
懒汉式：延迟创建，节省启动时间，但需要处理并发问题
         → 最佳写法：静态内部类（兼具懒加载 + 线程安全 + 无锁）
Spring Bean：默认饿汉式行为，加 @Lazy 变懒汉式
