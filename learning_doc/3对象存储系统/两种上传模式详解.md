# 两种上传模式详解：后端流式上传 vs 预签名直传

> 本项目对象存储系统设计了两种截然不同的文件上传模式，分别用于不同的业务场景。理解它们的区别，需要先搞清楚一个核心问题：**文件数据究竟经过谁的手传到 OSS？**

---

## 一、两种模式的本质区别

```
模式一（后端流式上传）：
  前端 ──────文件数据──────> 后端 ──────文件数据──────> OSS
  文件数据先到后端，后端再转发给 OSS

模式二（预签名直传）：
  前端 ──获取签名──> 后端（只颁发签名，不碰数据）
  前端 ──────────────────────文件数据──────────────────> OSS
  文件数据直接从前端传到 OSS，后端全程不参与数据传输
```

**一句话总结**：
- 模式一：后端是"搬运工"，文件经过后端中转
- 模式二：后端是"签证官"，只负责开证明，前端自己去 OSS 办事

---

## 二、模式一：后端流式上传（用于头像）

### 2.1 完整流程

```
前端                              后端                        OSS
 │                                 │                          │
 │  POST /api/v1/profile/avatar    │                          │
 │  Content-Type: multipart/form-data                         │
 │  Body: 头像文件二进制数据         │                          │
 │────────────────────────────────>│                          │
 │                                 │                          │
 │                                 ├─ 1. 从请求中读取文件流    │
 │                                 │    file.getInputStream() │
 │                                 │                          │
 │                                 ├─ 2. 生成唯一 objectKey   │
 │                                 │    posts/{userId}-{ts}.jpg
 │                                 │                          │
 │                                 ├─ 3. 创建 OSSClient       │
 │                                 │                          │
 │                                 ├─ 4. 调用 putObject()     │
 │                                 │    把文件流推送给 OSS     │
 │                                 │─────────────────────────>│
 │                                 │                          │ 存储文件
 │                                 │<─────────────────────────│
 │                                 │                          │
 │                                 ├─ 5. 关闭 OSSClient       │
 │                                 │                          │
 │                                 ├─ 6. 生成公共访问 URL      │
 │                                 │    https://cdn.xx/posts/...
 │                                 │                          │
 │                                 ├─ 7. UPDATE users.avatar  │
 │                                 │                          │
 │  { avatarUrl: "https://..." }   │                          │
 │<────────────────────────────────│                          │
```

### 2.2 对应代码

```java
// OssStorageService.java
public String uploadAvatar(long userId, MultipartFile file) {
    ensureConfigured();

    // 步骤 2：生成 objectKey（用户ID + 时间戳 + 扩展名，保证唯一）
    String objectKey = props.getFolder() + "/" + userId + "-"
                     + Instant.now().toEpochMilli() + ext;

    // 步骤 3：每次请求新建 OSSClient（用完即关闭，防止连接泄漏）
    OSS client = new OSSClientBuilder().build(
        props.getEndpoint(),
        props.getAccessKeyId(),
        props.getAccessKeySecret()
    );

    try {
        // 步骤 4：把 MultipartFile 的输入流直接推给 OSS
        PutObjectRequest request = new PutObjectRequest(
            props.getBucket(),
            objectKey,
            file.getInputStream()   // ← 文件数据流，经过后端内存
        );
        client.putObject(request);
    } finally {
        client.shutdown();  // 步骤 5：无论成功失败都关闭连接
    }

    return publicUrl(objectKey);  // 步骤 6：返回可访问的 URL
}
```

### 2.3 数据在后端的流转

这里有个重要细节：文件数据不是"先全部存到后端磁盘，再发给 OSS"，而是**流式传输（Stream）**：

```
前端发来的文件数据：

  [前端网卡] ──网络包──> [后端网卡] ──内核缓冲区──> [JVM 堆内存]
                                                        │
                                          file.getInputStream()
                                                        │
                                                        ↓
                                          putObject(bucket, key, inputStream)
                                                        │
                                                   [OSS SDK]
                                                        │
                                          [后端网卡] ──网络包──> [OSS]
```

文件数据确实要经过后端的**内存和网络带宽**：
- 后端需要有足够的内存缓冲文件（Spring 默认最大 1MB，超过写临时文件）
- 后端需要消耗出方向的网络带宽把文件发给 OSS
- 后端需要等待上传完成，期间占用一个 HTTP 线程

## 三、模式二：预签名 PUT 直传（用于知文内容/图片/视频）

### 3.1 完整流程

```
前端                              后端                        OSS
 │                                 │                          │
 │  ① 申请预签名 URL               │                          │
 │  POST /api/v1/storage/presign   │                          │
 │  { postId, scene, contentType } │                          │
 │────────────────────────────────>│                          │
 │                                 │                          │
 │                                 ├─ 权限校验（postId 归属）  │
 │                                 │                          │
 │                                 ├─ 生成 objectKey          │
 │                                 │                          │
 │                                 ├─ 用 AccessKeySecret 签名 │
 │                                 │   生成带签名参数的 URL     │
 │                                 │  （不接触 OSS，纯本地计算）│
 │                                 │                          │
 │  { url: "https://oss...?        │                          │
 │    OSSAccessKeyId=xxx&          │                          │
 │    Expires=1735000000&          │                          │
 │    Signature=abc123",           │                          │
 │    objectKey: "posts/..." }     │                          │
 │<────────────────────────────────│                          │
 │                                 │                          │
 │  ② 前端直接 PUT 上传到 OSS      │                          │
 │  PUT https://oss...?签名参数    │                          │
 │  Content-Type: text/markdown    │  （后端完全不参与这一步） │
 │  Body: 文件二进制数据            │                          │
 │─────────────────────────────────────────────────────────>│
 │                                 │                          │ 验证签名
 │                                 │                          │ 存储文件
 │  200 OK                         │                          │
 │  ETag: "d41d8cd..."             │                          │
 │<─────────────────────────────────────────────────────────│
 │                                 │                          │
 │  ③ 通知后端上传完成             │                          │
 │  POST /api/v1/knowposts/{id}/content                       │
 │  { objectKey, etag, size, sha256 }                         │
 │────────────────────────────────>│                          │
 │                                 ├─ 写入 DB（content_url 等）│
 │<────────────────────────────────│                          │
```

### 3.2 预签名 URL 的生成——后端做了什么

预签名 URL 的核心是：**用后端持有的 AccessKeySecret 对请求参数做 HMAC-SHA1 签名，把签名结果拼在 URL 里，OSS 收到请求后用同一个密钥验证签名是否合法。**

```java
// OssStorageService.java
public String generatePresignedPutUrl(String objectKey, String contentType, int expiresInSeconds) {
    OSS client = new OSSClientBuilder().build(...);
    try {
        // 设置过期时间（当前时间 + 有效秒数）
        Date expiration = new Date(System.currentTimeMillis() + expiresInSeconds * 1000L);

        // 构造签名请求：指定 bucket、objectKey、HTTP 方法
        GeneratePresignedUrlRequest request = new GeneratePresignedUrlRequest(
            props.getBucket(),
            objectKey,
            HttpMethod.PUT   // ← 签名绑定 PUT 方法，不能用于 GET/DELETE
        );
        request.setExpiration(expiration);
        request.setContentType(contentType);  // ← 签名绑定 Content-Type

        // SDK 用 AccessKeySecret 做 HMAC-SHA1 签名，返回带签名参数的 URL
        // 注意：这一步完全在本地计算，不发任何网络请求
        URL url = client.generatePresignedUrl(request);
        return url.toString();
    } finally {
        client.shutdown();
    }
}
```

生成的 URL 长这样：

```
https://zhiguangapp.oss-cn-beijing.aliyuncs.com/posts/123/content.md
  ?OSSAccessKeyId=LTAI5tXXXXX          ← 标识是哪个账号的密钥
  &Expires=1735000600                   ← Unix 时间戳，过期时间
  &Signature=ZkJhb2XXXXX%3D            ← HMAC-SHA1 签名（URL编码）
  &Content-Type=text%2Fmarkdown        ← 签名绑定的 Content-Type
```

### 3.3 OSS 如何验证签名

OSS 收到前端的 PUT 请求后，做以下验证：

```
1. 检查 Expires 是否已超时
   当前时间 > 1735000600 → 返回 403 RequestTimeTooSkewed

2. 用账号对应的 AccessKeySecret 重新计算签名
   待签名字符串 = PUT\n\ntext/markdown\n1735000600\n/zhiguangapp/posts/123/content.md
   预期签名 = Base64(HMAC-SHA1(AccessKeySecret, 待签名字符串))

3. 比对请求中的 Signature 与预期签名是否一致
   不一致 → 返回 403 SignatureDoesNotMatch
   一致 → 允许写入
```

**关键：AccessKeySecret 只有后端知道，从不发给前端。** 前端拿到的 URL 里只有签名结果，无法从签名结果反推出密钥本身。

### 3.4 StorageController 的权限校验

注意，后端在颁发签名之前，做了一步关键的权限校验：

```java
// StorageController.java
long userId = jwtService.extractUserId(jwt);  // 从 JWT 提取当前用户

// 检查 postId 是否属于当前用户，防止 A 拿到 B 的草稿 ID 来上传
KnowPost post = knowPostMapper.findById(postId);
if (post == null || post.getCreatorId() != userId) {
    throw new BusinessException(ErrorCode.BAD_REQUEST, "草稿不存在或无权限");
}
```

这很重要：预签名 URL 一旦颁发，后端就不再参与上传过程。所以权限校验必须在颁发签名之前做，而不是等上传完成后再查。

## 四、为什么要设计两种模式

理解了两种模式的原理后，选择哪种模式的逻辑就非常清晰了。

### 核心矛盾：文件大小 vs 控制权

```
后端流式上传的代价（随文件大小线性增长）：
  后端内存消耗      =  文件大小  ×  并发上传数
  后端带宽消耗      =  文件大小  ×  上传频率
  后端 HTTP 线程占用 = 文件上传时长（大文件可能几十秒）

预签名直传的代价（固定，与文件大小无关）：
  后端只做一次签名计算（几毫秒，纯 CPU 计算）
  一个 HTTP 线程占用约 1ms（立即返回签名 URL）
```

### 为什么头像用后端上传

| 考量 | 说明 |
|------|------|
| **文件小** | 头像通常压缩后 < 200KB，中转代价可以接受 |
| **需要后端校验** | 必须验证是图片文件（非 PDF/exe/恶意脚本），后端可以检查 MIME 类型、文件头魔数 |
| **objectKey 由后端生成** | 头像路径格式为 `posts/{userId}-{timestamp}.jpg`，必须由后端控制，防止用户自行覆盖他人头像 |
| **直接写库** | 上传完成后立即更新 `users.avatar` 字段，流程简单 |

### 为什么知文内容/图片/视频用预签名直传

| 考量 | 说明 |
|------|------|
| **文件可能非常大** | 视频文件可达几百 MB 甚至 GB，经过后端中转会打满带宽，长时间占用线程 |
| **不需要后端处理内容** | 知文正文是 Markdown 文本，图片是前端压缩后的 PNG/JPEG，后端无需读取内容 |
| **权限已在签名前校验** | 颁发签名前已验证 postId 归属，直传不带来额外安全风险 |
| **OSS 天然支持大文件** | OSS 支持最大 5GB 的单次 PUT 上传，以及更大文件的分片上传，直传可充分利用这些能力 |

## 五、预签名 URL 的安全边界

预签名 URL 颁发出去之后，后端就失控了吗？并不是，有以下几道安全保障：

### 保障一：有效期限制（Expires）

```
expiresIn = 600 秒（10 分钟）

URL 在 10 分钟后自动失效，OSS 拒绝接受。
即使 URL 被截获，攻击者也只有极短的时间窗口。
```

### 保障二：Content-Type 绑定

```
签名中绑定了 Content-Type: text/markdown

如果攻击者尝试用这个 URL 上传一个 image/jpeg 文件：
  PUT https://oss...?Signature=xxx
  Content-Type: image/jpeg   ← 与签名不符

  OSS 重新计算签名时会包含 image/jpeg，
  与 URL 中的 Signature 不匹配 → 403 拒绝
```

### 保障三：objectKey 绑定

```
URL 只能用于上传到指定路径：
  posts/123/content.md

攻击者不能用这个 URL 覆盖其他路径的文件：
  posts/456/content.md  ← 不同路径，签名验证失败
```

### 保障四：HTTP 方法绑定

```
签名指定了 HttpMethod.PUT

不能用这个 URL 做 GET（读取）或 DELETE（删除）操作，
签名与方法不符 → 403 拒绝
```

## 六、两种模式完整对比

| 维度 | 后端流式上传 | 预签名直传 |
|------|------------|----------|
| **文件流经路径** | 前端 → 后端 → OSS | 前端 → OSS |
| **后端带宽消耗** | 有（入站 + 出站各一份） | 无（只有签名请求，几百字节） |
| **后端内存消耗** | 有（文件大小 × 并发数） | 无 |
| **后端 HTTP 线程占用** | 长（等待上传完成） | 短（签名计算后立即返回） |
| **适合文件大小** | 小文件（< 2MB） | 任意大小（GB 级视频） |
| **后端控制权** | 强（可读取、校验内容） | 弱（签名后不再参与） |
| **权限校验时机** | 上传时 | 颁发签名前 |
| **前端实现复杂度** | 低（直接 POST multipart） | 略高（需要两步：申请签名 + 直传） |
| **本项目使用场景** | 头像 | 知文正文、图片、视频 |

---

## 七、一句话总结

本项目设计两种上传模式，根本原因是**文件大小和控制需求的不同**：

- **头像**：文件小，需要后端校验文件合法性 → 后端中转可以接受，且更安全
- **知文内容/图片/视频**：文件可能很大，后端中转会浪费大量带宽和线程资源 → 后端只当"签证官"，颁发有时效的签名 URL，让前端直接和 OSS 对话

预签名直传是云存储的标准模式（AWS S3、阿里云 OSS 都支持），安全性靠签名时效（10分钟过期）、Content-Type 绑定、objectKey 绑定、HTTP 方法绑定四道机制保障。
