# 搜索系统详解

> 基于 Elasticsearch 构建内容搜索与联想建议功能，支持关键词检索、标签过滤，采用 `search_after` 游标分页保证深分页稳定性。通过 `function_score` 融合 BM25 相关性与业务权重优化排序，并使用 ES Completion Suggester 实现低延迟前缀联想。

## 三、关键词检索流程

### 3.1 搜索请求

```
GET /api/v1/search?q=Spring&size=10&tags=Java,后端&after=<cursor>
  │
  ▼
SearchServiceImpl.search(q, size, tagsCsv, after, currentUserId)
```

### 3.2 查询构造（Query DSL）

整个查询结构为 **function_score 包裹 bool 查询**：

```
function_score
  └─ query:
      bool
        ├─ must:
        │   multi_match(q, fields=["title^3", "body"])
        │       ^3 表示 title 字段匹配分值放大 3 倍
        │       BM25 算法：考虑词频(TF)、文档频率(IDF)、字段长度
        │
        ├─ filter:
        │   term(status, "published")     必须已发布
        │
        └─ filter（可选）:
            terms(tags, [tagList])        标签精确过滤（OR 关系）

  └─ functions:
      ├─ field_value_factor(like_count, modifier=log1p, weight=2.0)
      └─ field_value_factor(view_count,  modifier=log1p, weight=1.0)

  └─ boost_mode: sum
      最终分 = BM25相关性分 + 2×log1p(like_count) + 1×log1p(view_count)
```

### 3.3 function_score 详解

**`field_value_factor` + `log1p` 修饰符**：

```
原始权重 = log(1 + like_count)
```

使用 `log1p` 的原因：
- 点赞 0 → `log(1)=0`，不影响没有互动的内容
- 点赞 100 → `log(101)≈4.6`（适度加权）
- 点赞 10000 → `log(10001)≈9.2`（继续加权，但不会无限放大）
- 防止某热门内容的超高点赞数完全掩盖相关性低的问题

**`boost_mode: sum`**：

最终分 = BM25分 + 2×业务分1 + 1×业务分2，相关性与互动数据线性叠加（相比 `multiply` 模式更稳定）。

### 3.4 排序策略

```java
sorts = [
    score   DESC,         // 首要：综合分（相关性+互动）
    publish_time DESC,    // 次要：发布时间（新内容优先）
    like_count DESC,      // 三要：点赞数
    view_count DESC,      // 四要：浏览数
    content_id DESC       // 末位：content_id（保证排序完全稳定，防止相同分值时乱序）
]
```

**最后加 content_id 的必要性**：search_after 游标分页要求排序字段值唯一，content_id 作为兜底唯一键，确保每次分页结果稳定。

### 3.5 高亮处理

```java
.highlight(h -> h
    .fields(new NamedValue<>("title", ...))
    .fields(new NamedValue<>("body", ...))
)
```

ES 会在命中片段中将关键词用 `<em>` 标签包裹（可自定义）。

返回时合并高亮片段为 `snippet`：
```java
snippet = titleHighlights.join(" ") + " " + bodyHighlights.join(" ")
description = (snippet != null && !snippet.isBlank()) ? snippet : originalDescription
```

## 四、游标分页（search_after）

### 4.1 为什么不用 offset 分页

**offset 分页（from+size）的问题**：
- 深分页时，ES 需要先查出 `from+size` 条，再丢弃前 `from` 条，性能随 offset 增大急剧下降
- 当有新数据写入时，翻页可能出现重复或遗漏

**search_after 的优势**：
- 只需拿上一页最后一条的 sort 值作为游标
- 每次查询代价固定，不随翻页深度增加
- 结果稳定，不受新数据影响

### 4.2 游标编解码

**编码（当前页 → 下一页游标）**：
```java
// 取最后一条命中的 sort 值列表
List<FieldValue> sv = lastHit.sort();
// 转字符串拼接
String joined = parts.stream().map(this::fieldValueToString).collect(joining(","));
// Base64URL 编码（URL 安全，无需 URLEncode）
String nextAfter = Base64.getUrlEncoder().withoutPadding().encodeToString(joined.getBytes());
```

**解码（下一页请求 → sort 值）**：
```java
String decoded = new String(Base64.getUrlDecoder().decode(after));
// "3.14,1735000000,987654321"
String[] parts = decoded.split(",");
// index 0: Double（score）
// index 1: Long（publish_time 毫秒时间戳）
// index 2: Long（content_id）
List<FieldValue> afterValues = parseAfter(decoded);
```

### 4.3 前后端协议

```
首页请求：GET /api/v1/search?q=xxx&size=10
        响应：{items: [...], nextAfter: "abc123", hasMore: true}

翻页请求：GET /api/v1/search?q=xxx&size=10&after=abc123
        响应：{items: [...], nextAfter: "def456", hasMore: false}
```

## 五、联想建议（Completion Suggester）

### 5.1 请求

```
GET /api/v1/search/suggest?prefix=Spr&size=5
  │
  ▼
SearchServiceImpl.suggest("Spr", 5)
```

### 5.2 Completion Suggester 原理

ES Completion Suggester 使用 **FST（有限状态转换器）** 数据结构存储，专为前缀匹配优化：
- 构建时：将标题写入 `title_suggest` 字段（completion 类型）
- 查询时：前缀匹配，毫秒级响应（内存 FST 查找）

```java
es.search(s -> s.index(INDEX)
    .suggest(sug -> sug.suggesters("title_suggest",
        sc -> sc.prefix(prefix)  // 前缀
                .completion(c -> c.field("title_suggest").size(size))
    )),
    Map.class)
```

### 5.3 与普通 match 的区别

| 特性 | Completion Suggester | match 查询 |
|------|---------------------|-----------|
| 匹配方式 | 前缀匹配 | 全词匹配（分词后） |
| 数据结构 | FST（内存） | 倒排索引 |
| 响应速度 | 极快（<5ms） | 较快（10~50ms） |
| 适用场景 | 输入框实时提示 | 完整关键词搜索 |
| 支持模糊 | 有限（fuzzy参数） | 支持 |

### 6.3 增量维护（Canal Outbox 驱动）

```

    │ outboxMapper.insert(KnowPostPublished/MetadataUpdated/Deleted)
    ▼

    │

```

## 七、计数数据同步（最终一致性）

ES 中存储的 `like_count` / `view_count` 是从 Redis SDS 同步来的，存在短暂延迟：

```
用户点赞
  │
  ▼
Redis 位图 → Kafka → CounterAggregationConsumer → SDS 更新
  │
  ▼（定时或事件触发）
SearchIndexService.updateCounts(postId, likeCount, viewCount)
  → es.update → partial update
```

## 八、ES 客户端版本

项目使用 **ES Java new client**（`co.elastic.clients`），而非已废弃的旧版 `RestHighLevelClient`：

```java
// ElasticsearchConfig
RestClient restClient = RestClient.builder(httpHosts).build();
ElasticsearchTransport transport = new RestClientTransport(restClient, new JacksonJsonpMapper());
ElasticsearchClient client = new ElasticsearchClient(transport);
```

优势：
- 类型安全的 Builder 模式构造查询（编译期错误提示）
- 与 `co.elastic.clients.elasticsearch.core` 包的新 DSL 完全对齐
- 支持 Jackson 序列化器，天然与 Spring Boot 集成

## 九、设计亮点与学习要点

1. **BM25 + function_score 混合排序**：纯相关性排序会让很久以前的热门内容长期占据前排；加入发布时间和互动数据的权重，使结果更"新鲜"，同时保持相关性优先
2. **log1p 修饰符**：对业务指标做对数压缩，防止头部内容的超高数据完全碾压尾部内容，避免"马太效应"
3. **search_after 游标分页**：深分页性能稳定，无论翻到第几百页代价不变；而 from+size 方式第100页需要查 100×size 条再丢弃前 99×size 条
4. **Base64URL 游标编码**：sort 值序列化为字符串，Base64URL 编码后可直接放在 URL 参数中，无需 URLEncode
5. **Completion Suggester**：与普通搜索共用同一索引（不同字段），无需额外维护联想索引，数据一致性自然保证
6. **Outbox 模式驱动索引更新**：搜索索引与主库解耦，通过 Canal → Kafka 异步维护，主库写入不阻塞等待 ES 完成
7. **高亮 snippet**：优先展示 ES 高亮片段（关键词命中位置），不显示时 fallback 到 description 字段
