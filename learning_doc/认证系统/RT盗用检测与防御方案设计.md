# RT 盗用检测与防御方案设计

> **问题来源**：当前令牌轮换机制存在一个盲点——攻击者若比受害者先刷新 RT，受害者只会看到一次"普通的重新登录提示"，攻击者则持续持有有效会话，永远不会被感知到。本文设计一套完整的检测与响应方案。

---

## 一、先彻底理解当前的漏洞

### 现状

当前 `isTokenValid()` 只做一件事：查 Redis 键是否存在。

```java
// RedisRefreshTokenStore.java（当前实现）
public boolean isTokenValid(long userId, String tokenId) {
    String key = "auth:rt:{userId}:{jti}";
    return Objects.equals("1", redisTemplate.opsForValue().get(key));
}
```

结果只有两种：
- `true`：键存在，令牌有效
- `false`：键不存在，返回 `REFRESH_TOKEN_INVALID` → 前端提示重新登录

### 攻击场景复盘

```
时间线：

T0  用户登录，得到 RT-A（jti = "abc-123"）
    Redis: auth:rt:10001:abc-123 = "1"

T1  攻击者盗取 RT-A（例如通过 XSS、中间人攻击、设备丢失等）

T2  攻击者用 RT-A 刷新
    → RT-A 有效 → 签发 RT-B（jti = "xyz-456"）
    → Redis: auth:rt:10001:abc-123 删除，auth:rt:10001:xyz-456 = "1"
    → 攻击者持有 RT-B

T3  受害者（正常用户）用 RT-A 刷新（他还不知道 RT-A 已经被用过）
    → isTokenValid("abc-123") → false（键已被删）
    → 抛出 REFRESH_TOKEN_INVALID
    → 前端：弹出"登录已过期，请重新登录"
    → 受害者以为是正常过期，重新输入账号密码，登录成功，得到 RT-C

T4  此后：
    ├─ 受害者使用 RT-C 正常活动
    └─ 攻击者使用 RT-B 也在正常活动（永远不会被感知！）

关键问题：受害者永远不知道 T3 那次"重新登录"背后是 RT 被盗用了，
          双方都持有各自有效的 RT，互不干扰，攻击成功。
```

### 为什么当前设计没有预警能力？

根本原因：**RT 失效（键不存在）只有一个含义——"用过了或过期了"，系统无法区分是正常轮换消耗掉的，还是被别人抢先用了。**

你提出的核心洞察：
> "发现 RT 失效时，需要判断它是**自然过期**还是**提前被撤销**（即被别人用过了）。如果 RT 自身的 `exp` 还没到，但白名单里没有它，这是可疑的。"

这个洞察完全正确，这正是 [RFC 6819](https://www.rfc-editor.org/rfc/rfc6819) 和 [OAuth 2.0 Security Best Current Practice](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-security-topics) 中明确讨论的攻击模型，解决方案的学术名称是 **Refresh Token Theft Detection**。

## 二、你的方案分析与完善

你提出的思路：
1. RT 失效时，检查当前时间是否在 RT 的 `exp` 之后
2. 若 `exp` 未到但 RT 已从白名单消失 → 可疑
3. 不能直接提示改密码（可能是时间对齐问题）
4. 进一步比对 IP、UA 等信息来确认是否真的被盗

你的思路方向是对的，但有几个细节需要完善：

### 问题一：Redis 键消失 ≠ 一定是被盗用

有几种正常情况也会导致"RT 的 `exp` 未到，但 Redis 键不存在"：

| 场景 | 原因 |
|---|---|
| 正常轮换后，前端还拿着旧 RT | 刷新成功后旧 RT 被删，但前端因网络波动没收到响应，重试时用旧 RT 又来一次 |
| Redis 宕机重启 | 数据未持久化时所有白名单键丢失 |
| 主动登出后又用旧 RT | 用户主动登出（键被删），但同一浏览器另一 Tab 还有旧 RT |
| 时钟偏移 | 服务器时间和 JWT `exp` 的时钟有微小差异 |

所以仅凭"RT `exp` 未到 + 键不存在"就采取强力响应（比如冻结账号）是过激的。需要引入**可信度评分**，叠加多个维度综合判断。

### 问题二：比对 IP/UA 有局限性

你提到的 IP 和 UA 比对确实是主流方案，但有限制：
- IP 会变（用户从 WiFi 切换到 4G，从公司到家）
- UA 容易伪造（攻击者可以用相同的 UA 发请求）
- 国内运营商的 NAT 会让大量用户共享同一出口 IP

因此不能用 IP/UA 来**确认**是否被盗，只能用来**提升可疑程度的置信度**。

## 三、完整的防御方案设计

### 方案整体思路：三层防御

```
层级1：检测异常（被动感知）
  └─ 发现"RT exp 未到但键不存在"时，触发可疑事件分析

层级2：动态评估风险等级（风险评分）
  └─ 综合多个维度（IP变化、UA变化、地理位置、时间间隔等）计算可疑分数

层级3：分级响应（按风险等级采取不同措施）
  └─ 低风险 → 静默记录
     中风险 → 通知用户并引导验证
     高风险 → 撤销所有 RT + 强制重新登录
```

---

### 层级一：区分三种 RT 失效类型

当前只有一种处理：RT 不在白名单 → 报错。改造后需要区分：

**类型 A：RT 已自然过期**
```
判断条件：JWT 解码失败（NimbusJwtDecoder 抛出 JwtException，原因是 exp 过期）
处理：正常的"登录过期"，提示用户重新登录
```

**类型 B：RT 签名无效 / 格式错误**
```
判断条件：JWT 解码失败，原因是签名验证失败
处理：可能是伪造令牌，记录警告日志，提示重新登录
```

**类型 C：RT 签名有效且 exp 未到，但不在白名单（★可疑！）**
```
判断条件：
  - JWT 解码成功（签名有效、exp 未过期）
  - isTokenValid() 返回 false（键不存在）
处理：进入风险评估流程（见层级二）
```

这需要改造 `AuthService.refresh()` 里的异常处理逻辑，不再把"JWT解码失败"和"白名单不存在"统一抛同一个错误，而是区分处理。

---

### 层级二：多维度风险评分

当检测到"类型 C"可疑事件时，拉取更多上下文进行评分：

#### 评分维度设计

**维度1：令牌上一次使用的上下文（需要存储）**

当前 Redis 白名单只存了 `"1"`（占位符），要检测盗用，需要把令牌使用时的上下文一并存储：

```
键：auth:rt:{userId}:{jti}
值（改为 Hash 结构）：
  ├─ status    = "active"
  ├─ ip        = "1.2.3.4"        ← 发放令牌时的 IP
  ├─ ua        = "Mozilla/5.0..." ← 发放令牌时的 UA
  ├─ country   = "CN"             ← 发放时的地理位置（通过 IP 查询）
  ├─ issuedAt  = "1746424400"     ← 令牌签发时间戳
  └─ lastSeen  = "1746424400"     ← 最后一次合法使用的时间戳
```

**维度2：当前请求与上次记录的对比**

当发现类型 C 事件时，用当前请求的上下文与上面存储的信息比对：

| 维度 | 可疑分值 | 说明 |
|---|---|---|
| IP 变化到不同国家 | +50 | 中国 → 美国，极高可疑 |
| IP 变化到不同城市 | +20 | 上海 → 北京，中等可疑 |
| IP 变化到同城市 | +5 | 可能是换网，低可疑 |
| IP 未变化 | 0 | 正常 |
| UA 完全不同 | +30 | Chrome → curl，高可疑 |
| UA 略有差异 | +5 | 浏览器版本更新，低可疑 |
| 两次请求时间间隔极短（< 5秒） | +40 | 同时刷新，高可疑（竞态特征） |
| 距发放时间异常短（< 1分钟就来刷新） | +20 | 可能是自动化脚本 |

**维度3：历史行为基线**

从审计日志（`login_log` 表）查询该用户的历史登录 IP 地理分布，判断当前 IP 是否是"常用地区"：

```
用户历史登录：上海(50次)、杭州(10次)
当前 IP：上海 → 在历史范围内 → 扣10分（降低可疑度）
当前 IP：莫斯科 → 从未出现   → 加50分（极高可疑）
```

**维度4：是否存在"孤儿 RT" —— 被遗忘的子令牌链**

令牌轮换会形成一个链：RT-A → RT-B → RT-C（每次刷新产生下一个）。
如果 RT-A 被盗，攻击者用 RT-A 换到 RT-B，受害者用 RT-A 发现失效、重新登录得到 RT-C。

此时系统里 RT-B 是"孤儿"——它不属于任何从正常登录触发的链。
检测孤儿 RT 的方式：在白名单里存储令牌链的父子关系：

```
auth:rt:{userId}:{jti-B}:parent = {jti-A}   ← RT-B 的父 RT 是 RT-A
```

当受害者发现 RT-A 失效时，可以查询"以 RT-A 为 parent 的子令牌"是否存在于白名单——如果存在，说明 RT-A 确实被别人用过生成了 RT-B（这就是"孤儿 RT"），这是最强的盗用证据。

#### 综合评分与阈值

```
总分 = 各维度分值之和

分值区间        风险等级      触发动作
─────────────────────────────────────────────────────
0  ~ 20        低风险        记录可疑日志，提示重新登录（当前行为）
21 ~ 60        中风险        发送安全提醒（短信/邮件），要求完成二次验证
61 ~ 100       高风险        撤销该用户所有 RT + 强制重新登录 + 发送安全告警
100+           极高风险      撤销所有 RT + 临时锁定账号 + 人工审核
```

---

### 层级三：分级响应策略

#### 低风险响应（分值 0~20）

可能是用户正常换网或 Redis 异常导致的误判，不应该过激：

```
1. 记录可疑事件日志（异步，不阻塞响应）：
   {
     userId, suspiciousJti, currentIp, currentUa,
     score, reason:"rt_not_in_whitelist_within_exp",
     timestamp
   }
2. 返回 REFRESH_TOKEN_INVALID（与当前行为一致）
3. 前端提示"登录状态已失效，请重新登录"（不提及安全问题，避免误报引发恐慌）
```

#### 中风险响应（分值 21~60）

有一定可疑性，但不能确认，用"引导用户自证"代替强制措施：

```
1. 撤销当前 RT（如果是孤儿 RT，顺带撤销整条链）
2. 不撤销其他设备的 RT（避免误伤）
3. 向用户的手机/邮箱发送安全提醒：
   "您的账号在新设备/新地区尝试登录，如非本人操作，请立即修改密码"
4. 返回特殊错误码 SUSPICIOUS_TOKEN_ACTIVITY（而非普通的 REFRESH_TOKEN_INVALID）
5. 前端展示安全提示页，提供两个选项：
   ├─ "是我本人操作" → 正常重新登录
   └─ "不是我" → 引导修改密码（触发 revokeAll）
```

#### 高风险响应（分值 61+）

证据较充分，采取保护性强制措施：

```
1. 立即撤销该用户所有 RT（revokeAll）
   → 攻击者和受害者的所有活跃会话全部失效
2. 发送紧急安全告警给用户（短信 + 邮件 + 站内信同时发送）：
   "您的账号可能遭受安全风险，我们已自动登出所有设备，请重新登录并修改密码"
3. 将账号标记为"安全审查中"，下次登录时强制要求二次验证（短信/邮件验证码）
4. 记录完整的安全事件到专用审计表（安全日志，不是普通登录日志）
5. 返回 ACCOUNT_SECURITY_LOCKDOWN 错误码
```

### 关于"时间对齐"问题的处理（你提到的）

你担心的"可能只是时间上没有完全对齐"确实存在，主要是以下场景：

**场景：网络重试导致的误判**

```
T0  前端用 RT-A 请求刷新接口
T1  服务器处理成功：删除 RT-A，创建 RT-B，正在返回响应...
T2  网络超时，前端没收到响应
T3  前端重试，再次用 RT-A 请求刷新
T4  服务器：RT-A 不存在 → 可疑事件？！

这是误判！RT-A 是被上次成功处理消耗的，不是被盗
```

**解决方案：引入"宽容窗口"机制**

在白名单存储里，不是直接删除旧 RT，而是先把它标记为 `"used"` 并保留一小段时间（如 30 秒）：

```
正常轮换时：
  旧键 auth:rt:{userId}:{old-jti} 的值从 "1" 改为 "used"，TTL 设为 30 秒
  新键 auth:rt:{userId}:{new-jti} = "1"，TTL = 7 天

当有人用旧 jti 来刷新时：
  值为 "1"   → 正常有效，走刷新流程
  值为 "used" → 最近 30 秒内被合法消耗（极可能是网络重试），返回"请用新令牌"
               同时检查该用户是否已有更新的 RT 存活，若有则返回提示"请刷新页面重试"
  键不存在   → 超过 30 秒窗口，进入可疑事件分析流程
```

这个宽容窗口把"刚被正常消耗"和"很久前被别人用过"区分开来，大幅降低误判率。

## 四、令牌链溯源：孤儿 RT 检测的实现思路

这是方案中最精巧的部分，值得单独说明。

### 存储令牌链关系

每次签发新 RT 时，额外记录它的"来源"：

```
登录时签发 RT-A：
  auth:rt:10001:jti-A = { status:"active", parentJti:"LOGIN", ip:"...", ... }

RT-A 刷新得到 RT-B：
  auth:rt:10001:jti-B = { status:"active", parentJti:"jti-A", ip:"...", ... }
  auth:rt:10001:jti-A 值改为 "used"（保留 30 秒）

RT-B 刷新得到 RT-C：
  auth:rt:10001:jti-C = { status:"active", parentJti:"jti-B", ip:"...", ... }
  auth:rt:10001:jti-B 值改为 "used"
```

### 检测孤儿 RT

当 RT-A 被盗，攻击者先用 RT-A 换到 RT-B，受害者再用 RT-A 时发现失效：

```
受害者用 RT-A：
  查 auth:rt:10001:jti-A → 不存在（已过宽容窗口）或值为 "used"

  进入孤儿检测：
  查询：有没有 parentJti = jti-A 的活跃子令牌？

  扫描 auth:rt:10001:* 的所有 Hash，找 parentJti = jti-A 的项
  → 找到 auth:rt:10001:jti-B（parentJti = jti-A, status = active）
  → jti-B 是孤儿！它是 RT-A 被别人使用后生成的

  这是高强度的盗用证据：
  → 立即撤销 jti-B（和它的所有子链）
  → 触发高风险响应：revokeAll + 安全告警
```

### 为什么孤儿 RT 是强证据？

```
正常情况下的令牌链：
  LOGIN → RT-A → RT-B → RT-C（用户自己一路刷新）

被盗后的令牌树（分叉！）：
             RT-A（已消耗）
            /              \
        RT-B（攻击者分支）  RT-C（受害者重新登录后的分支）

出现分叉就意味着 RT-A 被使用了两次——
一次生成 RT-B（攻击者），一次试图生成 RT-C（被拒绝了，受害者只能重登）。
正常的令牌轮换不可能出现分叉。
```

## 六、现有代码需要改造的关键点

> 本节仅描述改造思路，不修改代码，供后续实现参考。

1. **`RedisRefreshTokenStore`**：白名单值从 `"1"` 改为 Hash，存储 IP、UA、parentJti、status 等字段；撤销时改为设置 status = "used" + 30 秒宽容窗口，而非直接删除键。

2. **`AuthService.refresh()`**：将"白名单失效"的错误路径拆分为"宽容窗口内"和"可疑事件"两条分支；可疑事件路径引入风险评分引擎。

3. **新增 `SuspiciousTokenDetector`（安全检测服务）**：封装孤儿 RT 检测、多维度评分、风险等级判定逻辑，与 `AuthService` 解耦。

4. **新增 `SecurityEventService`（安全事件服务）**：封装分级响应动作（记录日志、发通知、撤销、锁定），异步执行不阻塞刷新接口的正常响应。

5. **扩展 `LoginLog`（或新建 `SecurityEvent` 表）**：记录可疑事件、风险评分详情、最终采取的动作，供安全审计使用。

## 七、补充：行业内的真实实践

- **Google**：实现了称为 "Refresh Token Binding" 的机制，将 RT 与设备指纹（Device ID）绑定。跨设备使用同一 RT 直接触发告警并撤销。
- **GitHub**：2021 年在 OAuth App 的 RT 机制中引入了"RT 重用检测"，检测到 RT 被重用时会立即撤销整个授权，并向用户发送邮件通知。
- **Auth0 / Okta（商业身份服务）**：提供 "Refresh Token Rotation + Automatic Reuse Detection" 作为默认功能，逻辑与本文孤儿 RT 检测基本一致。
- **Spotify**：使用 RT 绑定设备类型，RT 只能在同类型设备上使用（PC 端 RT 不能在移动端使用），跨类型使用触发撤销。
