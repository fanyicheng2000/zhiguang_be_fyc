# 全局异常管理器详解

> **你的问题**：全局异常管理器是什么？有什么用？为什么要这么设计？我对这个概念非常模糊。

---

## 一、先理解"没有全局异常管理器时"会发生什么

假设你在 `AuthService.login()` 里发现账号不存在，你需要告诉前端"账号不存在"。

**方案A（糟糕的做法）：每个 Controller 方法自己处理异常**

```java
@PostMapping("/login")
public ResponseEntity<?> login(@RequestBody LoginRequest request) {
    try {
        AuthResponse response = authService.login(request, ...);
        return ResponseEntity.ok(response);
    } catch (BusinessException ex) {
        // 每个接口都要写这段
        Map<String, Object> error = new HashMap<>();
        error.put("code", ex.getErrorCode().getCode());
        error.put("message", ex.getMessage());
        return ResponseEntity.badRequest().body(error);
    } catch (MethodArgumentNotValidException ex) {
        // 参数校验失败，又要写一遍
        // ...
    } catch (Exception ex) {
        // 未知异常，又要写一遍
        // ...
    }
}
```

项目有几十个接口，每个都要写这段重复代码，任何一个遗漏都会导致前端收到格式混乱的响应（甚至是 Spring 默认的 HTML 错误页）。这是典型的**代码重复问题**。

**方案B（本项目的做法）：全局异常管理器**

```java
// 所有接口都不捕获异常，直接抛出即可
@PostMapping("/login")
public AuthResponse login(@RequestBody LoginRequest request) {
    return authService.login(request, ...);  // 干净！没有 try-catch
}

// 所有异常的处理逻辑集中在一个地方
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<?> handle(BusinessException ex) { ... }
}
```

全局异常管理器的本质是：**把分散在各处的 try-catch 集中到一个地方统一处理**。

---

## 二、Spring 是怎么实现这个机制的

### @RestControllerAdvice 的工作原理

```java
// GlobalExceptionHandler.java
@RestControllerAdvice   // ← 这个注解是核心
public class GlobalExceptionHandler { ... }
```

`@RestControllerAdvice` = `@ControllerAdvice` + `@ResponseBody`

`@ControllerAdvice` 的意思是："这个类是所有 Controller 的**增强（Advice）**，对所有 Controller 生效"。它是 Spring AOP（面向切面编程）的一个应用——在不修改任何 Controller 代码的前提下，为所有 Controller 添加统一的异常处理逻辑。

**工作流程**：

```
请求进入 Controller 方法
    │
    ▼
Controller 方法执行，某处 throw BusinessException
    │
    ▼
异常沿调用栈向上传播
    │
    ▼
Spring MVC 的 DispatcherServlet 捕获到这个异常
    │
    ▼
DispatcherServlet 查找：有没有 @ExceptionHandler 能处理 BusinessException？
    │
    ├─ 有 → 调用 GlobalExceptionHandler.handleBusiness(ex)，返回其结果
    └─ 没有 → 继续向上抛，最终可能变成 500 错误页
```

### @ExceptionHandler 的匹配规则

```java
@ExceptionHandler(BusinessException.class)       // 精确匹配 BusinessException
public ResponseEntity<?> handleBusiness(...) { }

@ExceptionHandler(MethodArgumentNotValidException.class)  // 精确匹配参数校验异常
public ResponseEntity<?> handleValidation(...) { }

@ExceptionHandler(Exception.class)               // 兜底，匹配所有未被处理的异常
public ResponseEntity<?> handleGeneric(...) { }
```

**匹配优先级**：先找最具体的类型，再找父类型。`BusinessException` 也是 `Exception` 的子类，但 Spring 会优先用 `handleBusiness`（更具体）而不是 `handleGeneric`（更宽泛）。

## 三、本项目的 GlobalExceptionHandler 逐一解析

```java
// GlobalExceptionHandler.java
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {
```

`@Slf4j` 是 Lombok 提供的日志注解，自动生成 `private static final Logger log = ...`。

### 处理器1：业务异常 → HTTP 400

```java
@ExceptionHandler(BusinessException.class)
public ResponseEntity<Map<String, Object>> handleBusiness(BusinessException ex) {
    Map<String, Object> body = new HashMap<>();
    body.put("code", ex.getErrorCode().getCode());   // 如 "IDENTIFIER_NOT_FOUND"
    body.put("message", ex.getMessage());             // 如 "账号不存在"
    return ResponseEntity.badRequest().body(body);    // HTTP 400
}
```

`BusinessException` 是项目自定义的异常类，持有一个 `ErrorCode` 枚举：

```java
// BusinessException.java
public class BusinessException extends RuntimeException {
    private final ErrorCode errorCode;
    // ...
}

// ErrorCode.java（部分）
public enum ErrorCode {
    IDENTIFIER_NOT_FOUND("IDENTIFIER_NOT_FOUND", "账号不存在"),
    INVALID_CREDENTIALS("INVALID_CREDENTIALS", "登录凭证错误"),
    REFRESH_TOKEN_INVALID("REFRESH_TOKEN_INVALID", "刷新令牌无效"),
    BAD_REQUEST("BAD_REQUEST", "请求参数错误"),
    // ...
}
```

前端收到的响应：
```json
HTTP 400 Bad Request
{
  "code": "IDENTIFIER_NOT_FOUND",
  "message": "账号不存在"
}
```

**为什么用 ErrorCode 枚举而不是直接传字符串？**

`code` 字段是给**程序读**的（前端 switch-case 判断），`message` 是给**用户看**的。前端根据 `code` 做分支处理，比如：
```javascript
if (response.code === 'IDENTIFIER_NOT_FOUND') {
    showError('该账号未注册，请先注册');
} else if (response.code === 'INVALID_CREDENTIALS') {
    showError('密码错误，请重试');
}
```

用枚举管理 code，保证整个项目中相同错误的 code 字符串永远一致，不会出现一处写 `"user_not_found"`、另一处写 `"USER_NOT_FOUND"` 的混乱。

### 处理器2：参数校验失败（@Valid）→ HTTP 400

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<Map<String, Object>> handleValidation(MethodArgumentNotValidException ex) {
    String message = ex.getBindingResult().getFieldErrors().stream()
            .findFirst()
            .map(FieldError::getDefaultMessage)
            .orElse(ErrorCode.BAD_REQUEST.getDefaultMessage());
    Map<String, Object> body = new HashMap<>();
    body.put("code", ErrorCode.BAD_REQUEST.getCode());
    body.put("message", message);
    return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(body);
}
```

当 Controller 参数上有 `@Valid` 注解，且请求体不满足约束时（如 `@NotBlank` 字段为空），Spring 会抛出 `MethodArgumentNotValidException`。

**触发场景**：
```java
// RegisterRequest.java
public record RegisterRequest(
    @NotNull(message = "账号类型不能为空") IdentifierType identifierType,
    @NotBlank(message = "账号不能为空")   String identifier,
    @NotBlank(message = "验证码不能为空") String code,
    // ...
) {}
```

前端发来 `{ "identifierType": "PHONE", "code": "123456" }`（缺少 `identifier` 字段），Spring 自动触发，全局处理器返回：
```json
HTTP 400 Bad Request
{
  "code": "BAD_REQUEST",
  "message": "账号不能为空"
}
```

`findFirst()` 只取第一个错误——如果多个字段都不合法，只报一个，避免前端一次收到一大堆错误信息。

### 处理器3：约束校验失败（@Validated 路径参数）→ HTTP 400

```java
@ExceptionHandler(ConstraintViolationException.class)
public ResponseEntity<Map<String, Object>> handleConstraintViolation(ConstraintViolationException ex) {
    Map<String, Object> body = new HashMap<>();
    body.put("code", ErrorCode.BAD_REQUEST.getCode());
    body.put("message", ex.getMessage());
    return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(body);
}
```

这个处理器与处理器2的区别：
- `MethodArgumentNotValidException`：用于 `@RequestBody` 对象的校验（`@Valid`）
- `ConstraintViolationException`：用于方法参数（路径变量、查询参数）的校验（`@Validated`）

比如 `GET /api/user/{userId}` 里如果 `userId` 有 `@Positive` 约束，传了负数就触发这个。

### 处理器4：未知异常兜底 → HTTP 500

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<Map<String, Object>> handleGeneric(Exception ex) {
    log.error("Unhandled exception", ex);  // ← 记录完整堆栈到日志
    Map<String, Object> body = new HashMap<>();
    body.put("code", "INTERNAL_ERROR");
    body.put("message", "服务异常，请稍后重试");  // ← 不暴露内部细节
    return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(body);
}
```

这是最重要的一个处理器：**捕获所有未预期的异常**。

两个关键设计：
1. `log.error("Unhandled exception", ex)`：把完整的异常堆栈写入日志，方便排查 Bug，但不暴露给前端
2. 返回 `"服务异常，请稍后重试"`：**不把内部错误信息（如 SQL 语句、NPE 的类名）暴露给客户端**，防止信息泄露

如果没有这个兜底处理器，Spring 默认会返回类似这样的响应：
```json
{
  "timestamp": "2026-05-17T10:00:00.000+00:00",
  "status": 500,
  "error": "Internal Server Error",
  "path": "/api/v1/auth/login",
  "trace": "java.lang.NullPointerException: Cannot invoke...\n\tat com.tongji..."
}
```

这把完整的堆栈暴露给了客户端，存在安全风险，且格式与业务响应不一致。

## 四、整体架构图

```
请求进入
  │
  ▼
Controller 方法
  │                    正常返回
  ├───────────────────────────────────► 200 响应
  │
  │ 抛出异常
  ▼
Spring MVC 异常处理机制
  │
  ▼
GlobalExceptionHandler（@RestControllerAdvice）
  │
  ├─ BusinessException             ──► HTTP 400，{ code, message }（业务错误）
  │                                                ↑
  │                                    ErrorCode 枚举保证 code 一致性
  │
  ├─ MethodArgumentNotValidException ─► HTTP 400，{ code, message }（参数校验）
  │
  ├─ ConstraintViolationException   ──► HTTP 400，{ code, message }（路径参数校验）
  │
  └─ Exception（兜底）              ──► HTTP 500，{ code:"INTERNAL_ERROR", message:"服务异常" }
                                                              ↑
                                              完整堆栈只写日志，不给前端看
```

## 五、为什么要这么设计——三个好处

### 好处1：响应格式统一

前端只需要学一种错误格式：
```json
{ "code": "错误码字符串", "message": "人类可读的提示" }
```
不管是业务错误、参数错误还是服务器崩了，格式都一样。

### 好处2：业务代码干净

`AuthService`、`VerificationService` 等业务逻辑层只需要专注于 `throw new BusinessException(ErrorCode.XXX)`，完全不需要关心"怎么把这个异常变成 HTTP 响应"——那是全局异常处理器的事。职责分离，代码整洁。

### 好处3：安全防护

兜底处理器确保**任何未预期的异常都不会把内部细节泄露给客户端**，堆栈只进日志。

---

## 六、一句话总结

> 全局异常管理器（`@RestControllerAdvice` + `@ExceptionHandler`）是 Spring 提供的 AOP 机制，把所有 Controller 的异常处理逻辑集中在一个地方，保证：业务代码只管抛异常、不管怎么响应；前端永远收到格式统一的错误 JSON；内部错误细节不泄露给外部。
