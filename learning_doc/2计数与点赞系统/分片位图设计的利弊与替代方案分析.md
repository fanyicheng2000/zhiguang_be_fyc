# 分片位图设计的利弊与替代方案分析

> 本文围绕计数系统中"分片位图（Sharded Bitmap）"这一核心设计展开，分析其在不同场景下的真实价值、固有缺陷，并结合 Hash 和 ZSet 两种替代方案进行系统性对比，最终给出选型建议。

---

## 一、先把问题说清楚：分片位图到底在解决什么

在回答"是否过度设计"之前，必须先搞清楚位图在这里承担了哪些职责。

```
分片位图负责的事：
  ┌──────────────────────────────────────────────────────┐
  │  1. 幂等判重：用户是否已经点赞过？（防止重复计数）          │
  │  2. 真实计数：BITCOUNT 统计当前有多少人点了赞              │
  │  3. 状态查询：某用户是否点了赞？（isLiked 接口）           │
  └──────────────────────────────────────────────────────┘
```

这三件事是捆绑在一起的。**位图不是单纯为了"记录点赞行为"而存在，而是同时充当了事实层（fact layer）——计数的原始依据。**

---

## 二、你提出的核心质疑：分片导致空间浪费

你的直觉是对的，我们来量化地看一下。

### 2.1 分片逻辑回顾

```java
// BitmapShard.java
CHUNK_SIZE = 32_768  (2^15)

chunk = userId / 32768   // 定位第几个分片
bit   = userId % 32768   // 分片内的 bit 偏移
```

每个分片最多容纳 32768 个用户，占 **4KB**（32768 bit ÷ 8 = 4096 字节）。

### 2.2 Redis 位图的特性：按最大偏移量分配

Redis 的 String 类型在 SETBIT 时，会按照 **最大 offset** 分配内存，中间未设置的 bit 全部为 0。

具体来说，同一分片内只要有一个用户点了赞，Redis 就要为这个分片分配完整的 4KB：

```
分片 chunk=5（userId 163840~196607）：
  假设只有用户 163841 点了赞（bit=1）
  → Redis 为 key bm:like:knowpost:xxx:5 分配 4KB
  → 实际有效信息：1 bit（几乎全是 0）
  → 空间利用率：0.003%
```

### 2.3 用户 ID 分散时的放大效应

假设某篇文章被 100 个用户点赞，这 100 个用户的 ID 分散在不同 chunk：

```
用户 ID 分布示例：
  用户 A：userId = 1001       → chunk=0
  用户 B：userId = 45000      → chunk=1
  用户 C：userId = 90000      → chunk=2
  用户 D：userId = 200000     → chunk=6
  ...（100 个用户分散在 100 个 chunk）

结果：
  - 分片数量：100 个
  - 每片内存：4KB
  - 总内存消耗：100 × 4KB = 400KB
  - 存储的有效信息：100 个 1 bit ≈ 13 字节
  - 空间利用率：0.003%
```

**你的判断是准确的：当用户 ID 分散时，分片利用率极低，可能产生严重的内存浪费。**

## 三、你提出的替代方案分析

### 方案 A：Hash 记录点赞行为

```
Redis Hash 结构：
  key:   like:{entityType}:{entityId}
  field: userId（字符串形式）
  value: 1（或时间戳）

示例：
  HSET like:knowpost:123456  "1001"  "1"
  HSET like:knowpost:123456  "45000" "1"
  HEXISTS like:knowpost:123456 "1001"  → 1（判断是否点赞）
  HLEN like:knowpost:123456            → 总点赞数
```

**优点：**
- 空间利用率高：只存实际点赞的用户，100 个用户只占 100 个 field，无浪费
- 天然支持"点赞列表"查询（HGETALL）
- 无需分片，key 结构简单

**缺点：**

| 问题 | 说明 |
|------|------|
| **热门内容形成大 Key** | 百万点赞 → 单个 Hash 有百万个 field，Redis 内存集中，读写变慢 |
| **HLEN 有成本** | Hash 的元素数量存在 `listpack` 与 `ziplist/hashtable` 的内部转换，大 Hash 占内存更多 |
| **无法直接统计总数（O(N) 问题）** | HLEN 虽然是 O(1)，但内部 hashtable 结构在数据量大时比位图的 BITCOUNT 消耗更多内存 |
| **无法高效枚举点赞用户** | HGETALL 百万 field 是一次 O(N) 阻塞操作 |

### 方案 B：ZSet 记录点赞时间

```
Redis ZSet 结构：
  key:   like:{entityType}:{entityId}
  member: userId
  score:  点赞时间戳（Unix ms）

示例：
  ZADD like:knowpost:123456 1716000000000  "1001"
  ZSCORE like:knowpost:123456 "1001"        → 时间戳（存在则已点赞）
  ZCARD like:knowpost:123456                → 总点赞数
  ZRANGEBYSCORE ...                         → 某时间段内的点赞用户
```

**优点：**
- 同样空间利用率高，无分片浪费
- 额外支持"按时间排序"、"最近点赞的人"等业务需求
- ZSCORE 可以同时判断是否点赞 + 获取时间

**缺点：**

| 问题 | 说明 |
|------|------|
| **内存消耗更大** | ZSet 每个成员需要存 member + score（double 8字节），比 Hash 还重 |
| **依然是大 Key 问题** | 百万点赞 → 百万成员 ZSet，更严重 |
| **仅在"需要时间维度"时才有价值** | 如果只是判重+计数，ZSet 的 score 是冗余的 |

## 四、分片位图的真正价值：它在哪些场景下是对的

在反驳之前，我们要先承认：**分片位图并不总是错的**。它的设计在特定假设下非常高效。

### 4.1 用户 ID 连续且密集时

如果平台用户 ID 是自增的，且活跃用户 ID 分布比较连续（如 1 万~50 万区间有 80% 的活跃用户），那么同一分片内可能会有大量用户点赞，**利用率会大幅提升**：

```
假设文章被 10,000 个用户点赞，ID 分布在 [0, 200000] 区间：
  分片数量：200000 / 32768 ≈ 7 个分片
  总内存：7 × 4KB = 28KB
  有效信息：10000 bit ≈ 1.2KB
  利用率：约 4%（相比前面的 0.003% 已有质的改善）

当点赞数达到 50,000（同区间密集分布）：
  利用率提升到约 20%，接近合理范围
```

**结论：当用户 ID 连续分配 + 活跃用户密集时，分片位图的空间效率可以接受。**

### 4.2 BITCOUNT 的统计成本极低

`BITCOUNT key` 是 Redis 的原生命令，底层用了 SWAR（SIMD within a Register）算法，统计 4KB 位图中的 1 的个数只需几微秒，远快于 HLEN 的 Hash 查找链表遍历。

### 4.3 GETBIT/SETBIT 的幂等判重无与伦比

```
位图判重：  O(1) 时间，O(1) 空间（只是翻转一个 bit）
Hash 判重：  O(1) 时间，但每条记录至少几十字节
```

对于**亿级用户**，如果某篇超级热文有 5000 万点赞：
- 位图：最多占用 `最大userId / 8` 字节，且密集时利用率极高
- Hash/ZSet：5000 万 field/member，单个 key 占用数 GB，直接崩溃

## 五、这个设计真正的问题

抛开用户 ID 分布假设，这个设计有几个**真实存在的工程瑕疵**：

### 5.1 用 `KEYS` 命令枚举分片——生产事故级别的隐患

```java
// CounterServiceImpl.java:422
Set<String> keys = redis.keys(pattern);  // ← 这一行
```

`KEYS` 命令是全局扫描，在 Redis 中会 **阻塞所有其他请求**，直到扫描完成。这在 key 数量多时是生产级别的性能事故。代码注释里也写明了：

```java
// 生产环境建议以索引集合替代 KEYS
```

**但"建议"终究是建议，这个坑仍然存在于代码里。**

**正确做法**：维护一个 `SET bm:like:knowpost:123456:shards → {0, 1, 2, 5, 6}`，点赞时同步 SADD，重建时直接 SMEMBERS 拿到分片列表，完全绕开 KEYS。

### 5.2 分片 TTL 与过期管理缺失

现有代码没有为位图分片设置过期时间（TTL）。一篇文章如果随着时间推移点赞量不再增长，位图会长期占用内存而永不释放。

对于小流量平台，几个月后可能积累大量"僵尸位图"。

### 5.3 重建路径依赖 `KEYS`，形成"修复路径"的死循环

SDS 丢失 → 触发重建 → 执行 `KEYS bm:*` → 阻塞 Redis → 其他读写超时 → 触发更多重建 → 更多 `KEYS`... 这是一个潜在的雪崩路径。

### 5.4 分片粒度（32768）可能是拍脑袋的

```java
public static final int CHUNK_SIZE = 32_768;
```

没有任何注释说明为什么是 32768，而不是 65536 或 16384。不同 chunk 大小对内存效率、热点分布的影响是不同的，这个常量缺乏依据。

## 六、综合对比：三种方案在不同维度的表现

| 维度 | 分片位图 | Hash | ZSet |
|------|---------|------|------|
| **空间效率（ID 稀疏）** | ❌ 极差（大量零位） | ✅ 好（按需存储） | ✅ 好（按需存储） |
| **空间效率（ID 密集）** | ✅ 较好 | ✅ 好 | ⚠️ 较差（score 额外开销） |
| **幂等判重性能** | ✅ GETBIT O(1) | ✅ HEXISTS O(1) | ✅ ZSCORE O(log N) |
| **统计总计数** | ✅ BITCOUNT 极快 | ✅ HLEN O(1) | ✅ ZCARD O(1) |
| **超大规模点赞（亿级）** | ✅ 位图天然紧凑 | ❌ 大 Key 灾难 | ❌ 大 Key 灾难 |
| **支持时间排序** | ❌ 不支持 | ❌ 不支持（需单独存） | ✅ 天然支持 |
| **支持"谁点了赞"列表** | ❌ 需遍历位 | ✅ HGETALL | ✅ ZRANGE |
| **冷数据自动清理** | ❌ 无 TTL 机制 | ⚠️ 可设置 TTL | ⚠️ 可设置 TTL |
| **大 Key 风险** | ✅ 天然分片 | ❌ 热门内容必然大 Key | ❌ 热门内容必然大 Key |
| **重建成本** | ⚠️ BITCOUNT 全分片扫描 | ✅ HLEN 直接读 | ✅ ZCARD 直接读 |

## 七、结论：是过度设计吗？

答案是：**"这是一个有明确场景假设的设计，但该假设未被明确说明，且实现中存在几处明显的工程瑕疵。"**

### 7.1 设计本身的合理性

分片位图这个方案本身不是"过度设计"，它是工业界在**超大规模点赞场景**下的成熟方案：

- **微博、B站**这类平台，单篇内容点赞量可达千万，Hash/ZSet 的大 Key 问题会把 Redis 整个拖垮
- 位图的内存上限是可预期的（`最大userId / 8`），不会因为点赞数增长而无限膨胀
- BITCOUNT 的统计速度无可替代

但这个合理性建立在一个**隐含假设**上：**用户 ID 是连续分配的，活跃用户密集**。如果这个假设不成立（例如 ID 使用雪花算法，高位是时间戳，ID 天然稀疏），分片位图就会退化成你描述的"内存浪费机器"。

### 7.2 Hash/ZSet 替代方案的适用场景

| 方案 | 适合 |
|------|-----|
| Hash | 用户规模 <100 万，单内容点赞数 <10 万，需要"谁点了赞"功能 |
| ZSet | 需要按时间查询"最近点赞"、"点赞榜单"等时序需求 |
| 分片位图 | 亿级用户，百万级点赞，ID 分配连续，只需要"是否点赞"和"点赞总数" |

对于本项目（知文/笔记类中型平台），用户体量可能在百万以内，Hash 方案完全可以胜任，且代码更简单，不需要分片逻辑，也不需要复杂的 SDS 重建机制。

### 7.3 真正需要修的问题

无论保留哪种方案，以下问题都**必须修复**：

1. **删掉 `redis.keys(pattern)`**，改为维护分片索引集合（SET 类型），否则迟早在生产上出事
2. **为位图分片设置 TTL**，防止冷数据永久驻留内存
3. **明确 CHUNK_SIZE 的选择依据**，加上注释说明

## 八、如果你来重新设计

如果从零开始，针对中型平台（百万用户、百万内容、单内容最高万级点赞），一个更简洁的方案可能是：

```
幂等判重：  Hash（field=userId, value=1）
                 key: like:{entityType}:{entityId}
                 当点赞数超过阈值（如 10 万）自动迁移到位图

计数快照：  独立 String 存储（INCR/DECR 原子操作）
                 key: cnt:{entityType}:{entityId}
                 直接原子递增，无需 Kafka 聚合，无需 SDS 重建

时间排序：  ZSet（仅在需要时创建）
                 key: like:ts:{entityType}:{entityId}
                 score=时间戳，用于"最近点赞"等场景
```

这样：
- **小体量内容**：Hash 判重 + String 计数，简单高效
- **爆款内容**：当 HLEN 超过阈值，自动迁移到位图，避免大 Key
- **时间维度**：按需挂载 ZSet，不强制所有内容都存

## 九、学习收获

| 思维方式 | 说明 |
|---------|------|
| **先问"解决什么问题"** | 位图解决的是亿级场景的内存和速度问题，脱离场景评价设计是无意义的 |
| **警惕隐含假设** | 分片位图的效率依赖 "ID 连续" 这一未被明说的假设 |
| **工程细节决定成败** | `KEYS` 命令、缺少 TTL 这类细节，是让一个好设计变成事故的关键 |
| **没有银弹** | Hash/ZSet/Bitmap 各有适用场景，选型要量体裁衣 |
