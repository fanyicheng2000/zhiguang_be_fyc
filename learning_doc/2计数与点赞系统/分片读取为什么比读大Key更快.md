# 分片读取为什么比读大 Key 更快

> 直觉上"100 次操作"比"1 次操作"应该更慢，但在 Redis 中，读取 100 个分片 key，往往比一次读取一个等量大 key 更快。本文从 Redis 底层原理出发，解释清楚这个看似反直觉的结论。

---

## 一、先把问题说清楚

我们对比的是两种方案：

```
方案 A（大 Key）：
  一个 Hash key → 100 万个 field
  一次 HGETALL → 返回所有 field

方案 B（分片）：
  100 个分片 key，每片 1 万个 field
  Pipeline 发送 100 个 BITCOUNT 命令（节省 RTT）
```

**重要前提**：Redis 主线程是单线程串行执行命令的。无论是 Pipeline 发 100 条命令，还是发 1 条大命令，主线程都要把所有工作执行完才能处理下一个请求。**Pipeline 只节省网络往返时间（RTT），对主线程执行时间没有影响。**

因此，"分片比大 Key 快"的根本原因，**不在于 Pipeline**，而在于分片本身改变了每次操作的数据量和内存访问模式。

---

## 二、理解 Redis 的执行模型：单线程 + 事件循环

Redis 的命令处理是**单线程串行**的，底层基于 I/O 多路复用（epoll/kqueue）：

```
┌─────────────────────────────────────────────────────────────┐
│                     Redis 主线程                             │
│                                                             │
│  ┌─────────┐    ┌──────────┐    ┌──────────┐    ┌───────┐  │
│  │ 接收请求 │ →  │ 解析命令 │ →  │ 执行命令 │ →  │ 返回  │  │
│  └─────────┘    └──────────┘    └──────────┘    └───────┘  │
│        ↑                              ↑                     │
│   epoll 事件                    单线程串行执行               │
│   （可同时监听多个连接）           （一次只执行一条）          │
└─────────────────────────────────────────────────────────────┘
```

**关键约束**：命令执行阶段是单线程的，一条命令执行完才能执行下一条。

这意味着：**一条命令的执行时间，直接等于"其他所有命令"的等待时间**。

## 三、大 Key 操作为什么慢

### 3.1 HGETALL 的执行过程

当执行 `HGETALL big_hash`（100 万个 field）时，Redis 内部做了什么？

```
Redis 的 Hash 内部数据结构：
  - 小 Hash（≤128 个 field）：listpack（紧凑链表，内存连续）
  - 大 Hash（>128 个 field）：hashtable（链地址法哈希表）

HGETALL 在 hashtable 上的执行过程：
  1. 遍历 hashtable 的每个 bucket（桶）
  2. 对每个 bucket 遍历链表（处理哈希冲突）
  3. 对每个 entry：
     a. 读取 key 指针 → 解引用 → 复制 key 字节
     b. 读取 value 指针 → 解引用 → 复制 value 字节
     c. 追加到响应缓冲区
  4. 100 万个 field → 重复步骤 3，共 100 万次

时间复杂度：O(N)，N = field 数量
```

具体来说，假设每个 field 的处理耗时 100ns（内存访问 + 复制）：

```
100 万个 field × 100ns = 100ms

在这 100ms 内，主线程完全被 HGETALL 占用，
所有其他命令在队列中等待。
```

### 3.2 内存访问模式：Cache Miss 的代价

这里有一个更底层的原因——**内存访问的局部性**。

现代 CPU 有多级缓存（L1/L2/L3 Cache），访问缓存中的数据比访问主内存快 10~100 倍：

```
访问延迟对比：
  L1 Cache：~4 cycle  ≈ 1ns
  L2 Cache：~12 cycle ≈ 3ns
  L3 Cache：~40 cycle ≈ 10ns
  主内存（RAM）：       ≈ 60~100ns
```

Hash 的 hashtable 结构，每个 entry 是一个独立的堆内存分配（通过 jemalloc 分配），它们散落在内存的各个位置，**没有空间局部性**：

```
hashtable 的内存布局（示意）：

  bucket[0] → entry_A（地址 0x1000）
              field_A（地址 0x2340）
              value_A（地址 0x5600）
  bucket[1] → entry_B（地址 0x8900）
              field_B（地址 0xA120）
              ...

每访问一个 entry，都可能发生 Cache Miss（数据不在 L1/L2 缓存中），
需要从主内存重新加载，耗时 60~100ns。

100 万个 entry，假设 50% 发生 Cache Miss：
  500,000 次 Cache Miss × 70ns = 35ms 纯等内存时间
```

**大 Key 越大，Cache Miss 越多，遍历越慢。**

## 四、分片为什么快：两个真正的原因

### 原因一：每条命令的工作量小了

分片把 100 万个 field 拆成 100 个分片，每片 1 万个 field。

```
方案 A：主线程执行 1 次 HGETALL（100 万 field）
  阻塞时间 ≈ 55ms
  其他用户的请求等待 55ms

方案 B：主线程依次执行 100 次 BITCOUNT（每次 1 万 bit / 4KB）
  每次 ≈ 5μs，100 次合计 ≈ 0.5ms
  其他用户的请求最多等待 5μs（一条小命令的时间）

主线程阻塞时间：55ms → 0.5ms，缩短 110 倍
```

注意：方案 B 中主线程仍然是串行执行 100 条命令的，**总工作量相近，但每条命令的"持锁时间"从 55ms 变成了 5μs**，大幅减少了对其他请求的阻塞。

### 原因二：内存连续，Cache 命中率高

分片位图底层是 SDS（简单动态字符串），是**连续字节数组**：

```
分片位图（String/SDS 结构）：
  bit[0]   bit[1]   bit[2]   ...  bit[32767]
  ↑───────────────── 连续的 4KB 内存 ──────────────────↑

  第一次访问把 4KB 加载进 L2/L3 Cache 后，
  后续所有访问全部 Cache Hit，CPU 全速处理，无需等主内存。

大 Key（Hash，hashtable 结构）：
  entry 散落在堆内存各处，
  每次访问下一个 entry 几乎必然 Cache Miss，
  等主内存 60~100ns，累积下来耗时巨大。
```

BITCOUNT 底层使用 **SWAR 算法**，专门针对连续位数组优化：

```
SWAR 算法核心思路（以 64 位寄存器为例）：
  一次把 8 字节（64 个 bit）加载进寄存器
  用位运算并行统计 64 个 bit 中 1 的数量
  → 一条机器指令处理 64 bit

4KB = 32768 bit → 只需 512 次操作即可完成，约 2~5μs。

现代 CPU 有 POPCNT 指令（统计 1 的个数），
Redis 在支持的硬件上会直接使用，进一步加速。
```

## 五、Pipeline 的作用是什么（以及它不是什么）

分清楚两个问题很重要：

### Pipeline 解决的是：客户端等待时间（RTT）

正常情况下，每条命令都需要一次完整的网络往返：

```
客户端                        Redis 服务端
   |─── 命令1 ────────────────>|
   |                           |  ← 执行（1μs）
   |<── 响应1 ─────────────────|
   |       （等待 RTT ≈ 1ms）   |
   |─── 命令2 ────────────────>|
   ...

100 条命令：客户端等待 100 × 1ms = 100ms（其中 99.9% 是等网络）
```

Pipeline 把 100 条命令打包一次发出，只需 1 次往返：

```
客户端                              Redis 服务端
   |─── 100 条命令一起发 ─────────>  |  ← 依次执行（主线程串行）
   |<── 100 条响应一起收 ────────── |

客户端等待：1 × RTT = 1ms（网络等待从 100ms 降到 1ms）
主线程执行时间：不变，仍然是串行执行 100 条命令的总时间
```

### Pipeline 不解决的是：主线程执行时间

```
不用 Pipeline，发 100 条小命令：
  主线程执行时间 = 100 × 5μs = 0.5ms

用 Pipeline，发 100 条小命令：
  主线程执行时间 = 100 × 5μs = 0.5ms（完全相同）

Pipeline 对主线程阻塞时间没有任何影响。
```

### 两种优化的正确定位

| 手段 | 解决的问题 | 不解决的问题 |
|------|-----------|-------------|
| **分片（小 key）** | 主线程每次阻塞时间短；内存 Cache 友好 | 客户端多次 RTT |
| **Pipeline** | 客户端等待时间短（多次 RTT → 1 次） | 主线程执行时间 |

两者是**互补的**：分片让每条命令更快，Pipeline 让多条命令的网络开销更小。在读取多个分片 key 时，同时使用分片和 Pipeline 才能达到最优效果——但快的根本原因是分片，不是 Pipeline。

## 六、完整的性能对比

假设：100 万个用户点赞，存在一个 Hash 里（大 Key 方案），或 100 个分片（每片 1 万个 field）。

```
方案 A：大 Key，一次 HGETALL
  客户端等待 = 1 RTT + 主线程执行时间
             = 1ms + 55ms = 56ms
  主线程阻塞 = 55ms（期间所有其他命令排队）

方案 B：100 分片，Pipeline 100 条 BITCOUNT
  客户端等待 = 1 RTT（Pipeline）+ 主线程执行时间
             = 1ms + 0.5ms = 1.5ms
  主线程阻塞 = 0.5ms（每条 5μs，内存连续）

方案 B 快约 37 倍，原因分解：
  - 分片减少主线程阻塞：55ms → 0.5ms（贡献约 97%）
  - Pipeline 减少客户端 RTT：100ms → 1ms（在分片基础上锦上添花）
```

---

## 七、一句话总结

分片比大 Key 快，本质原因只有两个：

1. **每条命令工作量小**：O(N/100) vs O(N)，主线程阻塞时间缩短 100 倍
2. **内存访问友好**：SDS 连续字节 → Cache 命中率高，避免大量 Cache Miss；SWAR/POPCNT 硬件加速

Pipeline 是在使用多个分片 key 时顺带消除多次 RTT 的手段，是锦上添花，不是快的根本原因。
